# Changelog

All notable changes to Zinder are documented in this file. Zinder releases one
lockstep product version across its first-party crates, services, runtime
images, and API artifacts.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).


## [0.11.1] - 2026-11-14

### Fixed

- The `zinder-canonical-runtime` and `zinder-wallet-serving` images now carry `/usr/local/lib/zinder` as a traversable directory. In 0.11.0 the image build gave that directory mode 0644, which stopped the release from publishing images, binary archives, and a GitHub Release for that version. Zinder 0.11.0 exists only as the `zinder-core`, `zinder-proto`, and `zinder-client` crates; deploy 0.11.1 instead, which contains every 0.11.0 change. ([#174](https://github.com/ZcashFoundation/zinder/pull/174))


## [0.11.0] - 2026-11-14

### Added

- Zinder now certifies Zakura 1.8.6 as a node runtime alongside Zebra 7.0.0. The live and lightwalletd parity suites run against both nodes on the same Regtest schedule through NU7, nightly and on pull requests that touch node-facing code, and a release requires both nodes to pass. `deploy/zakura/regtest.toml` starts a Zakura Regtest node on that schedule. `deploy/zebra/regtest.toml` now includes the same zero-value NU6.1 lockbox disbursement that Zakura requires, so both nodes use the same funding configuration. ([#149](https://github.com/ZcashFoundation/zinder/pull/149))
- `zinder-ingest` can now reach a node's indexer gRPC endpoint over TLS, including mutual TLS, which a Zakura indexer on any non-loopback address requires. An `https://` `node.indexer_grpc_addr` negotiates TLS. The new `[node.indexer_tls]` section (`ca_cert_path`, `client_cert_path`, `client_key_path`, and `server_name`, or the matching `ZINDER_NODE__INDEXER_TLS__*` variables) names a CA bundle, a client certificate, and a client key as file paths, plus a TLS server name that overrides the hostname Zinder verifies in the node certificate. Ingest checks those files at startup and exits with a configuration error when one is missing or holds no certificate or key. On platforms that deliver secrets only as environment variables, the `zinder-canonical-runtime` and `zinder-wallet-serving` images accept `ZINDER_NODE__INDEXER_TLS__CA_CERT_PEM`, `ZINDER_NODE__INDEXER_TLS__CLIENT_CERT_PEM`, and `ZINDER_NODE__INDEXER_TLS__CLIENT_KEY_PEM`, and write them to files that only the `zinder` user can read. Every Zinder binary refuses these PEM variables when they are set directly. ([#150](https://github.com/ZcashFoundation/zinder/pull/150))
- Compose deployments can now stream mempool events from a node whose indexer gRPC listener requires mutual TLS, such as a Zakura node in another container. Merge `deploy/docker-compose.indexer-tls.yml`, set `ZINDER_NODE__INDEXER_GRPC_ADDR` to the node's `https://` indexer URL, and set `ZINDER_INDEXER_TLS_DIR` to a directory that holds `ca.pem`, `client.pem`, and `client-key.pem`. ([#151](https://github.com/ZcashFoundation/zinder/pull/151))

### Changed

- The single-host Compose deployment no longer defaults to a Zebra node in Z3. Compose refuses to start unless the env file sets `ZINDER_DEPLOY_NETWORK` (replacing `Z3_NETWORK_LOWER`), `ZINDER_SOURCE_NETWORK_NAME`, `ZINDER_SOURCE_COOKIE_VOLUME_NAME`, `ZINDER_NETWORK__NAME`, and `ZINDER_NODE__JSON_RPC_ADDR`. The checked-in env files now poll the mempool over JSON-RPC instead of streaming from `http://zebra:8155`. New `deploy/.env.zakura-mainnet` and `deploy/.env.zakura-testnet` files attach a Zakura node, and `deploy/node-cookie-permissions.yml` makes a non-Z3 node's cookie readable to Zinder. Update `/etc/zinder/env` as the VM deployment runbook describes before upgrading. ([#144](https://github.com/ZcashFoundation/zinder/pull/144))
- `zinder-ingest` now refuses to start against a pruned node. At startup it reads `pruned` from `getblockchaininfo` and requires the new `historical_block_bodies` capability. A node that reports `pruned: true` or omits the field makes readiness report `node_capability_missing`, and the process exits before it touches the store. This applies to restarts of an existing store too, so point ingest at an archive Zebra or Zakura node. `zinder-query` and `zinder-compat-lightwalletd` still accept pruned nodes. A Zakura node built by verified-commitment-trees fast sync permanently refuses tree states and subtree roots below its last checkpoint, and those refusals are now classed `capability_missing`. Native query returns them as the non-retryable `NODE_CAPABILITY_MISSING` instead of a retryable node error. ([#145](https://github.com/ZcashFoundation/zinder/pull/145))
- `zinder-ingest` now refuses to start when `ingest.construction.source_segment_max_blocks` (`ZINDER_INGEST__CONSTRUCTION__SOURCE_SEGMENT_MAX_BLOCKS`) is above 1000. Each block in a source segment is one JSON-RPC batch entry, and Zakura refuses batches with more than 1,000 entries. The default of 64 is unaffected. If you set a larger value, lower it to 1000 or less before upgrading. ([#146](https://github.com/ZcashFoundation/zinder/pull/146))
- The `zinder-wallet-serving` image now passes each process exactly the `ZINDER_*` variables its binary accepts, so any documented `zinder-ingest`, `zinder-projector`, or `zinder-query` variable, such as `ZINDER_PROJECTOR__BUILD__MAX_TEMPORARY_FILE_BYTES_PER_SORTER`, can be set on the container and reaches only the processes that read it. Variables no process reads are logged by name at startup. The construction deadlines are now set by `ZINDER_WALLET_SERVING__CANONICAL_CONSTRUCTION_DEADLINE_SECONDS` (default `10800`) and `ZINDER_WALLET_SERVING__WALLET_CONSTRUCTION_DEADLINE_SECONDS` (default `7200`), and any other `ZINDER_WALLET_SERVING__*` name stops the container at startup; a Mainnet build from an empty volume needs the longer values in the wallet-serving runbook. The image now refuses to start without `ZINDER_NODE__INDEXER_GRPC_ADDR`, because JSON-RPC mempool polling re-reads the whole mempool after every block and drops ingest readiness when that takes longer than 30 seconds; set it to the node's indexer gRPC URL before upgrading. The supervisor no longer restarts the container over occasional brief readiness drains: an answered unready stretch counts as a flap episode only after 60 seconds, while shorter drains still count toward the 900-second unready budget. ([#166](https://github.com/ZcashFoundation/zinder/pull/166))

### Fixed

- Reads pinned to a chain epoch with `at_epoch_id` no longer fail as soon as a new block arrives. `zinder-query` keeps serving the two most recently replaced epochs, each for up to one minute after it is replaced, so a wallet that reads the unspent outputs of its transparent receivers one by one under a single pin finishes across a new block instead of restarting. A `TransparentAddressTxIdsInRange` continuation resumes on the epoch that issued it during the same window. The first page of that history read carries no epoch pin and still answers only from the current epoch. On a transparent-serving `zinder-compat-lightwalletd`, `GetTaddressTxids` and `GetTaddressTransactions` read history and transactions at one epoch, so a new block during the request no longer fails it. Each retained epoch keeps its own canonical and wallet secondaries open, so the query process can hold up to four serving pairs at once, about 1.4 GiB on the `zinder-wallet-serving` image. ([#171](https://github.com/ZcashFoundation/zinder/pull/171))
- The default wallet-build spill ceiling no longer stops a Mainnet wallet build from genesis. A complete Mainnet build with the shipped wallet-serving image still needs longer construction deadlines (#158). `projector.build.max_temporary_file_bytes_per_sorter` (`ZINDER_PROJECTOR__BUILD__MAX_TEMPORARY_FILE_BYTES_PER_SORTER`) now defaults to 206158430208 (192 GiB) instead of 64 GiB, because the largest sorter of a Mainnet build needs about 99 GB. Several sorters spill at once, so keep about 130 GB free on the volume when a Mainnet wallet construction starts. When the setting is too small, `zinder-projector` now usually stops during the canonical scan instead of after it, with an error that names the setting and its environment variable. A refusal before a sorter has seen all of its records gives only a lower bound, so unset the setting or raise it well above that figure. Explicitly configured values are unchanged. ([#164](https://github.com/ZcashFoundation/zinder/pull/164))
- A `zinder-projector` that crashes or is killed during wallet construction now resumes as soon as it restarts with the same `projector.build_owner_hex`. Previously its leftover construction leases refused the restart for up to `projector.lease_duration_seconds`. A projector with a different owner value is still refused until the lease expires, and the error now names the owner that holds the build; the initial-sync runbook describes how to recover. A second projector running against the same wallet path is refused while the first builds, even with the same owner value, and a crash before the wallet store is created no longer blocks the next build. ([#167](https://github.com/ZcashFoundation/zinder/pull/167))
- `zinder-ingest` now stops within the wallet-serving supervisor's 20-second grace window when it is terminated while fresh canonical construction streams blocks. SST finalization and publication cannot be interrupted, so ingest finishes them before it exits. Construction stops without admitting a store, and the next start rebuilds it, or installs a staged READY store when publication had already finished. During construction, ingest no longer logs `mempool_durable_replay_failed` or `mempool_event_retention_failed` with `DeadlineExceeded`, because the mempool owner and mempool-event retention now start only after the writer admits a READY store. ([#168](https://github.com/ZcashFoundation/zinder/pull/168))
- Explorer views now publish the transparent-address ranking, so `ExplorerQuery.ServerInfo` advertises `explorer.transparent_address.activity_v2` and `explorer.transparent_address.ranking_v1`, and `TransparentAddressActivity` returns address summaries. A fresh Explorer views build includes the ranking from genesis. A store built by Zinder 0.10.0 needs no rebuild: after the upgrade, `zinder-ingest` builds the ranking from canonical history while the other views keep following the tip, logs `transparent_address_ranking_activated` when it serves, and resumes the build after a restart. ([#170](https://github.com/ZcashFoundation/zinder/pull/170))
- A new block no longer makes wallet serving briefly not ready. `zinder-ingest` keeps answering live mempool reads at the previous tip while it rebuilds the mempool view for the new one, so `MempoolSnapshot` no longer fails with "live mempool index is hydrating" after each block, and neither ingest (`syncing`) nor `zinder-query` (`ingest_control_unavailable`) withdraws readiness. A mempool read at the new tip waits up to five seconds for the rebuilt view. Ingest still reports `syncing` when its mempool view trails the canonical tip for 30 seconds. `zinder-query` and `zinder-compat-lightwalletd` also keep publishing new serving pairs while a long request, such as a transparent unspent-output read for an address with millions of outputs, holds an older one, so the reader no longer stalls at `replica_lagging` until a restart. ([#172](https://github.com/ZcashFoundation/zinder/pull/172))


## [0.10.0] - 2026-11-13

### Added

- Native `WalletQuery.TransparentOutpointSpendStatus` reports, for 1 to 1,024 transparent outpoints read at one chain epoch, whether each output is unspent, spent (with the spending transaction, input index, and block), or not found. It replaces `TransparentSpendsByOutpoint` and `TransparentUnspentOutputsByOutpoint` with one call, is served from the wallet projection without the Explorer views, and is advertised as `wallet.read.transparent_outpoint_spend_status_v1`. In `zinder-client`, call `ChainSnapshot::transparent_outpoint_spend_status`, which splits larger batches at one pinned epoch. A request with no outpoints or more than 1,024 fails with `INVALID_ARGUMENT` and the new `TRANSPARENT_OUTPOINT_COUNT_OUT_OF_RANGE` reason. On a store whose history starts after a checkpoint, a request that misses any outpoint fails with `FAILED_PRECONDITION` and `CANONICAL_HISTORY_UNAVAILABLE` instead of reporting it not found. The request reveals the outpoints a wallet tracks and, through them, the addresses that own them. ([#143](https://github.com/ZcashFoundation/zinder/pull/143))
- Broadcast results now distinguish transactions rejected for an unsupported transaction version (`UnsupportedTransactionVersion`, wire value 6) from transactions that exceed the per-block action limit (`ExceedsBlockActionLimit`, wire value 7), where both previously appeared as `Unknown`. `zinder-client` now decodes unspecified and unrecognized rejection reasons as `Unknown` instead of failing with `MalformedResponse`. Earlier `zinder-client` releases reject the new values, so release the client and update consumer pins before or together with the server. ([#134](https://github.com/ZcashFoundation/zinder/pull/134))
- Ingest now decodes blocks after NU7 activates (branch ID 0x77190ad9). Zinder 0.9.0 and earlier stop at the first NU7 block, so upgrade Zinder before the node serves NU7 blocks. ([#136](https://github.com/ZcashFoundation/zinder/pull/136))

### Changed

- Native `WalletQuery.CompactBlocksInRange` now sends the chain view once, as the first stream message, followed by bare compact blocks, instead of repeating the full chain view on every block. `CompactBlocksInRangeChunk` is now a `oneof body` with `header` and `item`. `zinder-client` keeps the same `compact_blocks_in_range` API and rejects a stream whose header is missing, repeated, or out of order with `MalformedResponse`. Upgrade notes: the native contract revision is now 7. Native query and ingest must run the same revision, so upgrade `zinder-ingest` and `zinder-query` together: `zinder-query` admits only an ingest at its own revision and fails at startup against a revision 6 `zinder-ingest`. No upgrade order is safe for native clients: a client built before this release fails on the first `CompactBlocksInRange` message from a new server, and this `zinder-client` refuses servers below revision 7. Release consumers such as Zally-based wallets on this `zinder-client`, then cut the Zinder services and those consumers over together. Raw gRPC consumers must read the leading header and take blocks from `body.item`. ([#142](https://github.com/ZcashFoundation/zinder/pull/142))
- Document the `GetLightdInfo` and `GetLatestBlock` identity contracts for lightwalletd compatibility, and compare tip-dependent fields in live parity tests only at equal tips. ([#135](https://github.com/ZcashFoundation/zinder/pull/135))
- Raw transaction bytes with trailing data now fail with RawTransactionParseFailed instead of being accepted for v1 to v4 transactions. Cipherscan avgBlockTimeSecs, the mining blockTime fallback, and the network-activity fallback interval now follow the target spacing at the block height (25 s from NU7) instead of a fixed 75 s. ([#136](https://github.com/ZcashFoundation/zinder/pull/136))
- Wallet build cold validation reads the flushed store back once per family and compares it with the construction digest instead of re-sorting the address families, which shortens large builds. The wallet build report replaces the two cold-validation sort durations with per-family scan durations, and the storage benchmark report format moves to version 4. ([#138](https://github.com/ZcashFoundation/zinder/pull/138))

### Removed

- Native `WalletQuery` now serves only the transparent reads its consumers need: `TransparentAddressUnspentOutputs`, ascending `TransparentAddressTxIdsInRange`, and `TransparentOutpointSpendStatus`. Removed, together with their capabilities and `zinder-client` methods: `TransparentAddressBalance`, `TransparentOutputsByOutpoint`, `TransparentSpendsByOutpoint` and `TransparentUnspentOutputsByOutpoint` (replaced by `TransparentOutpointSpendStatus`), the three transparent mempool lookups and their `IngestControl` methods, `TransparentUtxoSetSummary`, `ExplorerQuery.UtxoSetSummary`, and the `descending` history flag. The lightwalletd-compatible `GetTaddressBalance` is unchanged. Wallet and ingest `ServerInfo` and readiness no longer report `materialized_view_preset`; Explorer view identities are reported by `ExplorerServerInfo`. The `zinder_materialized_view_workload_info` metric is removed and `zinder_materialized_view_identity_info` loses its `preset` label. Upgrade notes: the native contract revision is now 8. Native query and ingest must run the same revision, so upgrade `zinder-ingest` and `zinder-query` together: `zinder-query` admits only an ingest at its own revision and fails at startup against a revision 7 `zinder-ingest`. No upgrade order is safe for native clients: a client built before this release receives `UNIMPLEMENTED` from a removed method on a new server, and this `zinder-client` refuses servers below revision 8. Release consumers such as Zally-based wallets on this `zinder-client`, then cut the Zinder services and those consumers over together. Explorer view stores built by earlier releases are refused at startup and must be rebuilt on a fresh materialized-view path (see the deploying-on-a-VM runbook). A client built before this release that sends `descending = true` now receives ascending results. Zallet's Zinder backend uses one removed item, the `descending` history flag: delete `descending: false` in `backends/zinder/src/chain.rs` and the test assertion on it. Its other `zinder-client` and `zinder-core` imports still exist. That was checked against the API surface, not by compiling Zallet, and upgrading it from `=0.6.0` also crosses every other breaking change since that release. ([#143](https://github.com/ZcashFoundation/zinder/pull/143))

### Fixed

- Native `WalletQuery.Transaction` and `zinder-client` now report a transaction as not found only when the absence is proven, so a wallet can safely treat `TxStatus::NotFound` as "never mined at this epoch". A proven absence is gRPC `NOT_FOUND` with the new reason `TRANSACTION_NOT_FOUND`, whose metadata names the epoch it covers, the covered heights, and whether the live mempool was searched. A pinned lookup (`at_epoch_id`, or a `ChainSnapshot`) covers that epoch's canonical chain only; an unpinned lookup also covers the writer's mempool at the same epoch. Storage faults, a missing or unserved epoch, and a block outside the best chain are now errors rather than `NotFound`. A store whose history starts after a checkpoint cannot prove an absence: it answers a miss with the new `CANONICAL_HISTORY_UNAVAILABLE` reason (`FAILED_PRECONDITION`, reported as `IndexerError::CanonicalHistoryUnavailable` with the first retained height), while an unpinned lookup still reports a pending transaction as in the mempool. On such a store, lightwalletd-compatible `GetTransaction` now fails a miss with `FAILED_PRECONDITION` instead of `NOT_FOUND`, and `is_in_mempool` fails with `CanonicalHistoryUnavailable` instead of returning `false` for a transaction that is neither pending nor mined above the floor. When the node reports a transaction mined in any block other than the tip the live mempool generation serves, ingest now ends that generation instead of removing the transaction, so live mempool reads return `UNAVAILABLE` until the next snapshot is certified rather than briefly reporting the transaction as absent from both the chain and the mempool. The mempool half of an unpinned absence remains best effort around reorgs; use a pinned lookup (`at_epoch_id` or a `ChainSnapshot`) for payment decisions. Upgrade notes: the native contract revision is now 6, and native query and ingest must run the same revision. The new client reports a `NOT_FOUND` from an older server as `IndexerError::TransactionAbsenceUnverified` instead of `NotFound`, so upgrade servers before relying on absences; an older client keeps reading every `NOT_FOUND` as `NotFound`. ([#105](https://github.com/ZcashFoundation/zinder/pull/105))
- The release verification commands in the deployment and release runbooks now name the `ZcashFoundation/zinder` repository. Releases from v0.8.0 onward are signed by `https://github.com/ZcashFoundation/zinder/.github/workflows/release.yml` and publish images under `ghcr.io/zcashfoundation/`, so the previously documented `gustavovalverde` identity and image path rejected genuine releases. ([#126](https://github.com/ZcashFoundation/zinder/pull/126))
- Compact-blocks `GetBlockRange` now omits transactions that the requested pool types leave with no data, such as a transparent-only coinbase under the default shielded selection, so range responses match lightwalletd. Remaining transactions keep their `CompactTx.index`. ([#137](https://github.com/ZcashFoundation/zinder/pull/137))
- RemoteChainIndex::mempool_events now fails the stream with MalformedResponse, before yielding the event, when a mempool event repeats or decreases event_sequence, reuses a cursor, or carries an empty cursor. Cursor retention is bounded to 65,536 cursors and 8 MiB per stream, matching chain events. ([#141](https://github.com/ZcashFoundation/zinder/pull/141))
- The lightwalletd-compatible service now matches lightwalletd for four requests wallet SDKs send. `GetLightdInfo.lightwalletProtocolVersion` reports the protocol release tag (`v0.5.0`) instead of a commit hash, so Zingo can sync. `GetAddressUtxos` and `GetAddressUtxosStream` with `maxEntries = 0` return every UTXO instead of silently stopping at 1,000, and fail with `RESOURCE_EXHAUSTED` above 100,000 rather than truncating. Transparent history accepts an absent, zero, or oversized `range.end` and reads to the tip. `GetTransaction` returns a transaction in the mempool at height 0, and answers `UNAVAILABLE` (retry) instead of `NOT_FOUND` when the mempool view is at a different epoch than the chain read. Upgrade notes for Rust users of `zinder-compat-lightwalletd`: `MempoolSurface` has a new required `mempool_transaction` method, and `DEFAULT_MAX_LIGHTWALLETD_ADDRESS_UTXOS` is now 100,000. ([#147](https://github.com/ZcashFoundation/zinder/pull/147))


## [0.9.0] - 2026-11-12

### Added

- Each release now publishes two more multi-architecture images for hosts that attach one volume to one container. `ghcr.io/zcashfoundation/zinder-wallet-serving` runs ingest, projector, and native query as supervised processes and omits lightwalletd compatibility. `ghcr.io/zcashfoundation/zinder-canonical-runtime` is the ingest-only diagnostic or canary runtime. Both carry the same provenance, SBOM, and signature evidence as the four runtime images, and neither is the complete supported topology. ([#128](https://github.com/gustavovalverde/zinder/pull/128))

### Removed

- `deploy/Dockerfile.wallet-serving`, `deploy/Dockerfile.railway-nocache`, `railway.toml`, `deploy/railway.canonical-runtime.toml`, and `deploy/railway.wallet-serving-runtime.toml` are removed, along with the `RAILWAY_DOCKER_TARGET_STAGE` build argument. Pull the published `zinder-wallet-serving` or `zinder-canonical-runtime` image instead, or build the target of that name from `deploy/Dockerfile`. Railway services must switch from a repository build to a Docker image source, then set the healthcheck path, healthcheck timeout, restart policy, and drain window in the service settings as the deployment runbooks describe. ([#128](https://github.com/gustavovalverde/zinder/pull/128))


## [0.8.0] - 2026-11-11

### Removed

- Ingest no longer accepts the configuration keys of its removed batch catch-up and tip-follow paths. Remove `ingest.construction.canonical_batch_max_blocks`, `canonical_batch_max_artifact_bytes`, `canonical_batch_max_estimated_write_bytes`, `canonical_batch_min_blocks_before_estimated_write_close`, `commit_reassembly_max_queued_artifact_bytes`, `flush_interval_epochs`, `ingest.run_overrides.allow_reorg_window_settlement`, and the ingest `storage.secondary_path` key, along with their `ZINDER_INGEST__*` environment variables, before upgrading: ingest refuses to start while any of them is set. The `zinder-ingest verify-canonical-replay` subcommand is removed; it could not open a canonical store written by the release ingest path. The storage benchmark drops its canonical-store range replay scenario and Compose profile, and the `ZinderStoreReadP95High` alert and its dashboard panel are removed because no release runtime emits the store read metrics they watched. Explorer methods that need canonical storage keep returning `FAILED_PRECONDITION` with `DEPENDENCY_NOT_CONFIGURED`, as they did before; the Cipherscan compatibility matrix now marks the routes that depend on them. ([#115](https://github.com/gustavovalverde/zinder/pull/115))

### Fixed

- Lightwalletd compatibility now refuses to start when its canonical secondary disagrees with the ingest writer fence on the visible block count, which it previously accepted. Native query now fails closed on a writer fence that diverges from its secondary instead of retrying it as replica lag until its attempts run out. Projector, native query, and lightwalletd compatibility now apply the same fence rules. ([#116](https://github.com/gustavovalverde/zinder/pull/116))
- Wallet reads served by `zinder-query` and `zinder-compat-lightwalletd` now record `zinder_query_request_*` metrics. Before, only operations proxied through the native adapter produced samples, so the `ZinderWalletQueryP95High` alert and the overview dashboard missed most wallet traffic. Expect new samples for every wallet read, including reads the serving store cannot answer. ([#117](https://github.com/gustavovalverde/zinder/pull/117))
- Explorer `/readyz` now reports `schema_mismatch` or `storage_unavailable` while its materialized-view catch-up fails, instead of staying ready. Ingest now stays `upstream_not_ready` until its Zebra health probe recovers; the follow loop no longer clears that cause, and `WriterStatus` reports the probe observation during construction and source recovery. When `[node.health]` is configured, ingest reports `starting` until the first successful probe instead of `ready`. Ingest, Explorer, and the Cipherscan adapter now report `shutting_down` as soon as termination is requested. ([#118](https://github.com/gustavovalverde/zinder/pull/118))
- A materialized-view rebuild that resumes without chain-event cursors after a reorg now reverts rows from the replaced chain before rebuilding, instead of keeping them. The transparent address activity index and the address ranking undo journals now write the same bytes regardless of hash-map order or batch size, so replaying the same chain produces identical materialized-view stores. ([#119](https://github.com/gustavovalverde/zinder/pull/119))
- Native `CompactBlocksInRange` and lightwalletd `GetBlockRange` now return `NOT_FOUND` with reason `ARTIFACT_UNAVAILABLE` for a range that reaches outside stored history, such as height 0 or a height below the retained floor, instead of `UNAVAILABLE`. A missing row inside retained history still reports a storage error, and `GetBlockRange` above the visible tip still returns `OUT_OF_RANGE`. ([#122](https://github.com/gustavovalverde/zinder/pull/122))
- Subtree-root reads on a checkpointed store now return `NOT_FOUND` with reason `ARTIFACT_UNAVAILABLE` for a root that completed below the retained history and was never loaded, instead of `UNAVAILABLE`. A missing root the store loaded, including any root of a store built with the complete subtree-root prefix, still reports a storage error. ([#123](https://github.com/gustavovalverde/zinder/pull/123))


## [0.7.0] - 2026-11-10

### Added

- Configure optional Explorer indexing and canonical compact-block compatibility at runtime without rebuilding the image; Explorer views default off and wallet serving remains independent. ([#88](https://github.com/gustavovalverde/zinder/pull/88))
- When ingest parks because a reorg exceeds its window, native query now refuses new wallet requests with `REORG_WINDOW_EXCEEDED`, carrying `replacement_depth_blocks` and `reorg_window_blocks` metadata, and ends open `ChainEvents` and `MempoolEvents` streams with the same status instead of leaving them idle on a chain that stopped advancing. Ingest also stops following the node mempool at the park, so it records no mempool events against the frozen fence. `zinder-compat-lightwalletd` refuses requests with the same status in both wallet and compact-block serving instead of reporting ready on the frozen tip, including while writer status is briefly unreachable. After an ingest restart, native query and compatibility report the new `canonical_tip_unconfirmed` readiness cause and refuse traffic until ingest has confirmed its stored tip against the node, which normally takes one poll; they stay unready while ingest cannot reach the node, rather than serve a tip the node may have abandoned. Upgrade ingest, the projector, native query, and compatibility together: the halt travels in new writer-status fields, so a reader from an earlier release keeps reporting ready against a parked writer. `zinder-client` reports it as `IndexerError::ReorgWindowExceeded` with retry policy `OperatorActionRequired`. The parked writer keeps serving its frozen fence to the projector and query, and the single-host wallet-serving image now keeps running in this state instead of restarting into the same park, so wallets keep receiving the typed refusal; its container `HEALTHCHECK` counts that state as healthy. ([#107](https://github.com/gustavovalverde/zinder/pull/107))

### Changed

- The README warns that Zinder is alpha and that native WalletQuery, lightwalletd compatibility, storage layouts, and deployment topology can still change. ([#96](https://github.com/gustavovalverde/zinder/pull/96))
- Existing canonical and wallet stores now start against a node that announces a future network upgrade, such as Zebra 7.0.0 adding NU7, without a rebuild. A node table that changes an upgrade the store has already passed is refused, and the store is left unchanged. Running query and lightwalletd-compatible services follow the newly admitted table without a restart. `GetLightdInfo` now reports the next pending upgrade in `upgradeName` and `upgradeHeight`, as the lightwalletd protocol defines, instead of the active one: NU7 and its activation height before NU7 activates, then an empty name and height 0 with NU7's `consensusBranchId`. The first start of this release writes schedule revision 1 to the canonical store even when the node's table is unchanged, so earlier Zinder releases can no longer open that store; upgrade all Zinder services together and restart ingest before the readers. Rust callers of `LightwalletdGrpcAdapter::new`, `with_response_limits`, and `from_admitted_compatibility_query` no longer pass an activation table. ([#106](https://github.com/gustavovalverde/zinder/pull/106))
- The default reorg window for ingest, projector, native query, and lightwalletd compatibility is now 1000 blocks, the depth past which Zebra 7 and Zakura finalize blocks, so ingest no longer parks on a reorg the node itself can produce. The settled tip, and every finality status derived from it, now trails the visible tip by up to 1000 blocks. Upgrade warning: deployments that rely on the default, on the shipped `deploy/config` files, or on the wallet-serving image move to 1000 on their first start, and that raise is irreversible: earlier Zinder releases cannot open the raised stores, and the window cannot be lowered in place. To keep a rollback path, capture a state bundle before starting this release. Deployments that set `reorg_window_blocks` explicitly keep their value. Starting ingest with a larger window raises an existing canonical store in place, and the projector raises the wallet store when it resumes, so restart ingest first, then the projector, native query, and compatibility with the same value. Replaceable depth grows to the new window as blocks arrive. A smaller window is refused and still requires a rebuild. A replacement now holds at most `ingest.follow.max_replacement_bytes` (2 GiB by default) of fetched and prepared blocks before its atomic commit and fails with `ReplacementBytesExceeded` beyond it; ingest then exits and retries on restart rather than parking, so raise the limit to follow such a reorg. Live commits and reader catch-ups now authenticate only the replay rows a transition changed, so their cost no longer grows with the window. Cipherscan `finality_status` now reports `Finalized` only for blocks at or below the settled tip instead of after 100 confirmations. ([#107](https://github.com/gustavovalverde/zinder/pull/107))

### Fixed

- The wallet projector no longer exits and crash-loops when the canonical writer commits while it is confirming the writer's position; it retries with backoff for up to projector.fence_convergence_timeout_seconds (default 30) and reports syncing if the lag lasts more than a second. A genuine mismatch between projector and writer still fails immediately. ([#97](https://github.com/gustavovalverde/zinder/pull/97))
- Ingest now waits for a node whose tip falls to or below the settled tip on the same branch, as after a Zebra restart, instead of parking with reorg_window_exceeded. ([#110](https://github.com/gustavovalverde/zinder/pull/110))

### Security

- HTTP/2 serving now uses a patched h2 crate so empty DATA frames cannot grow unbounded in memory. ([#96](https://github.com/gustavovalverde/zinder/pull/96))
- TLS connections now use rustls 0.23.45, which rejects TLS 1.3 handshake messages sent at the wrong encryption level (RUSTSEC-2026-0285). ([#97](https://github.com/gustavovalverde/zinder/pull/97))
- Dependencies now resolve to patched rustls, rustls-webpki, webpki-root-certs, tokio, libz-sys, zstd-sys, and pulldown-cmark releases that fix RUSTSEC-2026-0346 to 0349, 0382, 0383, 0386, 0410, 0414, 0418, and 0433. ([#111](https://github.com/gustavovalverde/zinder/pull/111))
