# Changelog

All notable changes to Zinder are documented in this file. Zinder releases one
lockstep product version across its first-party crates, services, runtime
images, and API artifacts.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).


## [0.26.0] - 2026-11-25

### Added

- Export canonical construction progress as `zinder_ingest_construction_loaded_height` and `zinder_ingest_construction_target_height` Prometheus gauges and update `/readyz` (`current_height`, `cause.syncing.lag_blocks`) and `zinder_readiness_sync_lag_blocks` while fresh canonical construction runs in `bulk_catchup`. ([#573](https://github.com/ZcashFoundation/zinder/pull/573))

### Changed

- Fresh wallet projection cold validation now splits the `transparent_address_transaction` readback across up to `projector.build.accumulator_hashing_workers` disjoint hash-prefix key ranges (at most one range per 65,536 rows), matching the parallel range scan already used for primary output families while producing byte-identical READY digests and row counts. ([#575](https://github.com/ZcashFoundation/zinder/pull/575))
- Fresh wallet projection construction now scans the settled canonical replay prefix in parallel 4,096-block height chunks across up to `projector.build.accumulator_hashing_workers` workers into sharded outpoint sorters (splitting `projector.build.max_outpoint_sort_memory_bytes` across workers while enforcing a single shared `projector.build.max_temporary_file_bytes_per_sorter` ceiling), flushing the final sharded runs in parallel during `outpoint_sort` while verifying every chunk boundary, the ordered canonical sequence digest, and the unsettled suffix identically. ([#576](https://github.com/ZcashFoundation/zinder/pull/576))
- Cached settled stored commitment-tree checkpoints in `zinder-query`'s in-memory `SettledStates` cache on `EveryBlock` canonical stores so repeated `GetTreeState` lookups for settled blocks serve preformatted cached entries instead of re-reading RocksDB and re-encoding hexadecimal tree state on every call, while leaving unsettled blocks uncached across tip reorgs and stale reader generations. ([#588](https://github.com/ZcashFoundation/zinder/pull/588))
- Raised the default wallet-projection RocksDB reader open-file limit (`wallet.rocksdb.max_open_files`) from `64` to `1024`, capped the wallet-projection writer live WAL ceiling (`wallet.rocksdb.max_wal_bytes`) at `32 MiB` (`33554432` bytes) while keeping materialized-view defaults unchanged, and enabled partitioned `10`-bits-per-key hybrid Ribbon filters with two-level index search and pinned top-level index and filter blocks on canonical `block_hash_index` and `transaction_location` column families and bulk SSTs. ([#589](https://github.com/ZcashFoundation/zinder/pull/589))
- Raised external sort merge fan-in up to `256` runs (automatically scaled down when process file-descriptor headroom is tight) and recycled half of `projector.build.max_outpoint_sort_memory_bytes` into the address-transaction sorter after outpoint sorting completes to eliminate intermediate merge spills during Mainnet wallet construction, added ancestor cgroup v2 `memory.max` and `memory.high` detection so processes honor systemd slice memory caps, created missing parent directories for `zinder-projector`'s canonical secondary path at startup, and reported exact configured paths and underlying error causes across `zinder-projector` and `publish-shielded-history`. ([#591](https://github.com/ZcashFoundation/zinder/pull/591))
- Parallelized settled `ZSHRNG01` segment construction and `fs-verity` sealing in `zinder-compat-lightwalletd publish-shielded-history` across bounded worker threads (`--workers <COUNT>`, `1..=16`, default `min(CPUs, 4)`) with batched manifest durability during initial bulk catchup while preserving strict sequential height ordering, atomic rollback guarantees, and unchanged on-disk formats. ([#604](https://github.com/ZcashFoundation/zinder/pull/604))
- Streamed `ZebraJsonRpc` batched `getblock` responses without `serde_json::Value` DOM allocation, offloaded hex decoding (`const-hex`) and block-header parsing onto blocking worker threads, skipped redundant `tip_id()` polls strictly below `tip_height - reorg_window_blocks` during fixed-tip construction (clarified in ADR-0006 Decision 6), and tightened proactive `SourceSegmentSizer` backoff on dense epochs. ([#605](https://github.com/ZcashFoundation/zinder/pull/605))
- Eliminated duplicate depth-32 checkpoint root derivation in `CommitmentTreeAccumulator::cross_checked_pool` and global `parking_lot::Mutex` contention in `with_frontier_root_memo`, partitioned `TreeHashers` worker pools so asynchronous checkpoint tasks do not stall block commitment appends, and parallelized large/multi-pool leaf commitment decoding during canonical store construction. ([#606](https://github.com/ZcashFoundation/zinder/pull/606))
- Pipelined bulk `OrderedSstWriter` SST compression and dual SHA-256 evidence hashing onto bounded-memory worker queues, overlapped secondary address-index and address-transaction sort-and-drain stages during multi-worker wallet projection construction, consolidated overlapping secondary phase labels into `secondary_address_derivation` on `zinder_wallet_projection_build_stage_duration_seconds`, and updated `ZINDER_PROJECTOR__BUILD__ACCUMULATOR_HASHING_WORKERS` configuration docs. ([#607](https://github.com/ZcashFoundation/zinder/pull/607))
- Compacted `zinder-compat-lightwalletd`'s in-memory `SealedHistory` index from `168` B/block to `45` B/block on Linux `fs-verity` segments and `109` B/block on portable filesystems by packing per-slab validation state into 1 byte per block, omitting redundant per-row parent and height metadata, and lazily reading per-row SHA-256 digests from `fs-verity`-verified segment files on first validation while preserving per-read digest verification on portable filesystems and leaving `ZSHRNG01` wire bytes unchanged. ([#608](https://github.com/ZcashFoundation/zinder/pull/608))
- Batched shielded commitment-tree appends across Sapling, Orchard, and Ironwood pools during bulk canonical construction when `checkpoint_selection != every_block` and hashing workers exceed one, wired optional build-time `ZINDER_PASTA_ASM` support into Docker and Compose deployment targets with runtime CPU feature guards in `zinder-bench`, and added `zinder_ingest_canonical_tree_append_duration_seconds`. ([#609](https://github.com/ZcashFoundation/zinder/pull/609))
- Wired `ZebraIndexerBlockSource` into `zinder-ingest` (`ingest.source = "zebra-indexer-grpc"`) with lazy failover validation across `[node]` and `[node_fallbacks.N]`, skipped redundant `tip_id()` polls on strictly settled history segments with continuity fallbacks, and prepared canonical blocks concurrently via byte-bounded out-of-order streams while preserving contiguous commit order. ([#610](https://github.com/ZcashFoundation/zinder/pull/610))
- Sharded wallet projection external sorting, draining, and SST writing across two-byte key prefixes while bounding concurrent merge descriptors and scaling default sort memory budgets from container memory limits. ([#613](https://github.com/ZcashFoundation/zinder/pull/613))

### Fixed

- Pre-register `zinder_node_rate_limited_total` and `zinder_compat_block_range_stream_refusals_total` at zero on startup with `# HELP` and `# TYPE` metadata so alerts and dashboards distinguish zero refusals from missing metrics. ([#572](https://github.com/ZcashFoundation/zinder/pull/572))
- Classify forwarded transparent UTXO and balance served-tip mismatches in `zinder-compat-lightwalletd` as `SERVED_TIP_MISMATCH` (`Code::Unavailable`) with `grpc-retry-pushback-ms: 1000` metadata instead of `NODE_UNAVAILABLE`, and allow one bounded `TipWait` catch-up retry when the backing node is ahead of the served view. ([#574](https://github.com/ZcashFoundation/zinder/pull/574))
- Fixed a CPU regression on warm unary gRPC responses and `GetTreeState` by eliminating spurious HTTP/2 release-gate reschedules on held terminal trailers while preserving full probe gating across all response sizes, removing per-request middleware boxing, mutex, and timer allocations on public gRPC listeners, fast-pathing `TipWait` when the requested height is at or below the visible tip, and moving warm settled tree-state cache hits onto a shared read lock with cached hexadecimal fields and zero per-call `height_band` string allocations. ([#577](https://github.com/ZcashFoundation/zinder/pull/577))
- Decoupled `zinder-history-publisher`'s default container memory ceiling (`ZINDER_HISTORY_PUBLISHER_MEMORY_LIMIT` set to `4g` Mainnet, `2g` Testnet, `1g` Regtest) from `ZINDER_COMPAT_MEMORY_LIMIT` and documented cgroup v2 `ZSHRNG01` page-cache sizing for high-concurrency Mainnet `zinder-compat-lightwalletd` deployments. ([#579](https://github.com/ZcashFoundation/zinder/pull/579))


## [0.25.0] - 2026-11-25

### Added

- Operators can export an Ed25519-signed canonical RocksDB snapshot and bootstrap an independent ingest writer from a local directory or HTTP(S). Bootstrap verifies the signed file inventory and checks consensus anchors against the configured validator before installing the store with fresh cursor authentication. ([#541](https://github.com/ZcashFoundation/zinder/pull/541))
- Export `rocksdb.live-sst-files-size` per data column family through `zinder_store_rocksdb_property` on primary stores and on the single newest active serving generation of canonical and wallet secondary readers (`canonical_secondary` and `wallet_secondary`) on the 15-second sampling cadence. ([#561](https://github.com/ZcashFoundation/zinder/pull/561))

### Changed

- Fresh wallet builds and wallet transitions hash rows more than twice as fast: the wallet row digest and the UTXO set commitment now expand each element with ChaCha12 keyed by a BLAKE2b hash instead of BLAKE2X. `zinder-core` replaces `UtxoSetCommitmentScheme::LtHash16` with `LtHash16ChaCha12` and adds `expand_lthash16_element`. On x86-64, release builds enable the ChaCha AVX-512 backend, which runs only on CPUs with AVX-512F and AVX-512VL and produces the same bytes as the AVX2 path. ([#526](https://github.com/ZcashFoundation/zinder/pull/526))
- The public gRPC listeners of zinder-query, zinder-compat-lightwalletd, and zinder-explorer now reset a stalled response stream at the 60 s send-stall timeout while the connection and its other streams stay open. HTTP/2 discards the stream's queued response data and frees its stream slot the next time it writes to the connection, and a connection that cannot write is closed by its write-stall bound. Before, a client that answered keepalive pings but stopped granting flow-control window kept them until it disconnected. A stalled client now sees a stream reset (CANCELLED in grpc-go, grpc-java, and tonic; UNAVAILABLE in gRPC Swift) instead of DEADLINE_EXCEEDED. A connection that, once a write blocks, neither writes 16 KiB nor finishes writing everything it had buffered within the timeout is closed. The native contract revision is now 15, so upgrade zinder-ingest together with zinder-query and wallet-mode zinder-compat-lightwalletd. Stalled GetBlockRange responses on the lightwalletd listener, which hand HTTP/2 slices of their stored blocks, are reset the same way, so those blocks are released with the stream's queued data instead of being kept until the client disconnects. A stream whose data the connection cannot write out within the timeout, because the socket is slow or shared with busy streams, is reset the same way. Stalled HTTP/2 wallet responses count as cancelled when reset before their final status is released. Browser clients receive an expired request deadline as a gRPC-Web cancellation in their negotiated encoding, with the configured CORS headers. ([#528](https://github.com/ZcashFoundation/zinder/pull/528))
- Zinder now uses schema v1 for canonical, wallet, and materialized-view stores. The native network contract remains at revision 15. Build fresh stores side by side before cutover, then capture new state bundles and recovery archives and regenerate benchmark fixtures and reports. Rust callers opening canonical secondaries must pass explicit CanonicalStoreRequirements. ([#535](https://github.com/ZcashFoundation/zinder/pull/535))
- Canonical schema v1 now stores the serialized transaction SHA-256 digest in each 72-byte transaction location value. Rebuild pre-release canonical stores that use the 40-byte layout. New canonical and wallet SSTs use compression selected by column family, with Zstandard level 3 for cold canonical data and LZ4 for frequently accessed data. ([#536](https://github.com/ZcashFoundation/zinder/pull/536))
- Sealed wallet-history segments use the unified ZSHRNG01 format that stores both the compact-block and the nullifier-only projection of every settled block. GetBlockRangeNullifiers now serves its range zero-copy from those segments and the in-memory tail instead of re-encoding stored rows, in both ascending and descending order, and a pool selection of Sapling and Orchard alone serves the same frames below Ironwood activation. A range request whose pool selection omits only Ironwood reads stored frames below activation and canonical rows above it. The 64 MiB tail budget now counts each cached row's shielded and nullifier frames together. Existing ZSHRNG02 catalogs are not readable by the new format: republish segments into a fresh catalog directory before switching readers. ([#538](https://github.com/ZcashFoundation/zinder/pull/538))
- Choose wallet for complete wallet history and a local transparent index without storing raw blobs. Mined transaction bodies are verified against the canonical transaction digest when fetched from the primary node. Choose wallet-archive to retain all raw blobs. Replace the removed light-wallet-qualification serving alias with light-wallet. ([#539](https://github.com/ZcashFoundation/zinder/pull/539))
- lightwalletd block reads that name a height one or two blocks past the reader's visible tip now wait up to 3 seconds for that block instead of failing at once, so a wallet that learned a new tip from another reader behind the same load balancer gets the block. This covers `GetBlock` and `GetBlockNullifiers` by height, the block-range and encoded block-range methods, and `GetTreeState` by height. When the wait expires, the method returns the status it returned before. Set the wait with `compat.tip_wait_ms` (`ZINDER_COMPAT__TIP_WAIT_MS`, 3000 by default, 0 restores the immediate answer), the window with `compat.tip_wait_max_blocks` (2 by default), and the concurrent waiters with `compat.tip_wait_max_waiters` (256 by default); the defaults are provisional until cross-region skew is measured. A non-zero wait shorter than twice `storage.secondary_catchup_interval_ms` now fails startup, so a reader with a catch-up interval above 1,500 ms must lower the interval, raise the wait, or set it to 0. New metrics `zinder_compat_tip_wait_total`, `zinder_compat_tip_wait_duration_seconds`, and `zinder_compat_tip_waiters` report the waits. Every public gRPC listener now answers a request whose `grpc-timeout` expires before its response starts with `DEADLINE_EXCEEDED` instead of `CANCELLED`, so `zinder_wallet_rpc_requests_total{grpc_code}` counts those requests as `deadline_exceeded`. ([#542](https://github.com/ZcashFoundation/zinder/pull/542))
- Wallet reads that `light-wallet` and lean `wallet` serving forward to the node, such as `GetTransaction`, transparent address history, and UTXO lookups, now wait up to 10 seconds for one of 32 shared node-call slots instead of failing at once, and repeated transaction lookups are served from a 64 MiB verified cache; tune them with `forwarded_read_max_concurrent`, `forwarded_read_wait_ms`, `forwarded_read_waiters_per_slot`, and `forwarded_transaction_cache_bytes` under `[query]` or `[compat]`. A read still refused after the wait returns `UNAVAILABLE` on the lightwalletd surface and `RESOURCE_EXHAUSTED` with the new `FORWARDED_READ_LIMIT_REACHED` reason natively, and the `zinder_forwarded_read_*` and `zinder_forwarded_transaction_cache_lookups_total` metrics report the queue. ([#565](https://github.com/ZcashFoundation/zinder/pull/565))

### Fixed

- Ingest rejects a mempool transaction that the node returns with extra bytes after it. Previously the entry was admitted, wallets received the extra bytes, and the Explorer and Cipherscan mempool reads failed to parse it. ([#532](https://github.com/ZcashFoundation/zinder/pull/532))
- A public gRPC listener that trusts the x-zinder-client-address header now accepts a bare IP address, such as the {client_ip_address} value a GCP Global External Application Load Balancer sends, and counts every connection from that address as one client in the receive limit. An ip:port header still keys each connection apart, so wallets behind a shared Tor exit stay separate. The listener raises each stream's HTTP/2 send buffer from hyper's ~400 KiB default to 1 MiB, and the native client raises its receive windows from hyper's 2 MiB stream, 5 MiB connection, and 16 KiB frame defaults to 4 MiB stream, 16 MiB connection, and a 64 KiB max frame. ([#537](https://github.com/ZcashFoundation/zinder/pull/537))
- A burst of blocks no longer freezes the wallet-serving tip for 30 to 60 seconds. The reader released a replaced serving pair only after its 60-second retention window, so four back-to-back blocks filled every secondary generation even when no client held an epoch to pin. It now keeps a replaced pair for the window only when a response exposed its chain epoch, and releases any other pair at once. `GetLatestBlock` and `GetLightdInfo` expose no epoch, so polling them no longer delays new blocks, and an epoch a response exposed stays readable for the full minute. ([#540](https://github.com/ZcashFoundation/zinder/pull/540))
- A lean wallet lookup that misses the canonical store now verifies the forwarding node against the served tip before it consults the live mempool or reports the transaction absent, in lightwalletd GetTransaction and the native transaction lookup. An unreachable or skewed node returns UNAVAILABLE. Tip checks in block-range requests no longer keep a replaced serving generation alive, and transaction broadcast, fee, and shielded-history refresh release their serving pair before waiting on the node or a file. ([#544](https://github.com/ZcashFoundation/zinder/pull/544))
- Lightwalletd block-range streams now release their admission slot as soon as the stream ends or returns a terminal error and finishes any in-flight chunk read, rather than waiting for the transport to drop the response body, eliminating spurious UNAVAILABLE refusals at the default concurrency limit. The bounded waiter queue for block-range stream slots is also raised from 1x to 3x compat.max_concurrent_block_range_streams (300 waiters by default, holding no chunk buffers while queued) while keeping the default 100 active stream slots. ([#560](https://github.com/ZcashFoundation/zinder/pull/560))
- When a Zebra node refuses a JSON-RPC call with HTTP 429 because it holds its connection limit, Zinder now reports it as the retryable `UNAVAILABLE` reason `NODE_RATE_LIMITED` instead of `NODE_UNAVAILABLE`, counts it in `zinder_node_rate_limited_total`, and moves a broadcast to the next configured node. Each process now keeps at most `node.max_concurrent_requests` calls (default 64) in flight to one node, and readiness probes no longer wait behind those calls. When several Zinder processes share one node, keep the sum of their limits below the node's connection limit. ([#562](https://github.com/ZcashFoundation/zinder/pull/562))


## [0.24.0] - 2026-11-23

### Added

- Operators can compare two wallet reader binaries on the same private fixture, verify block-range response bytes against an independent oracle, and evaluate paired results against their own performance tolerances. ([#469](https://github.com/ZcashFoundation/zinder/pull/469))
- Set `deployment.profile = "light-wallet"` in the standard ingest and compatibility binaries to serve wallets with complete compact history and without raw blobs or a wallet projection. Configure one node with transparent address indexes. Existing schema 7 stores can serve readers whose minimum requirements they meet. A canonical layout change requires a fresh store. A seven-day build-beside rollback period is optional. Keep the previous binaries and their matching store if you need a fallback. ([#507](https://github.com/ZcashFoundation/zinder/pull/507))
- The wallet range probe reports pauses between successive blocks so operators can compare the longest pause across verified requests and inspect the individual frame arrivals. ([#519](https://github.com/ZcashFoundation/zinder/pull/519))
- `zinder-projector` exports `zinder_wallet_projection_build_stage_duration_seconds`, a histogram labeled by `stage` with the wall time of each non-overlapping stage of a fresh wallet build, recorded when the build publishes READY. The stages are listed in the metrics reference. ([#524](https://github.com/ZcashFoundation/zinder/pull/524))
- `projector.build.accumulator_hashing_workers` (`ZINDER_PROJECTOR__BUILD__ACCUMULATOR_HASHING_WORKERS`) sets how many threads a fresh wallet build uses to hash rows into its projection digest and UTXO set commitment, and how many key ranges cold validation reads the unspent and spent output families in. It defaults to the logical CPUs the projector may use, at most 4, and accepts 1 to 64; the projector refuses a larger value at startup. A build therefore uses more CPU by default: a full Testnet wallet build finished about 48% sooner on 4 cores and 29% sooner on 2, with about 5% more total CPU time and the same memory and temporary disk. Set it to 1 to hash on the build thread as before. The published wallet is the same at any value. `zinder-core` adds `TransparentUtxoSetCommitment::combine`. ([#525](https://github.com/ZcashFoundation/zinder/pull/525))

### Changed

- The lightwalletd listener sends signed-history `GetBlockRange` blocks of 32 KiB or more from the stored segment without copying them into the gRPC encode buffer. Responses are unchanged. In `zinder-proto`, `EncodedBlockRangeStream` now yields `EncodedBlock`, a gRPC length-prefixed `CompactBlock` message, so custom `EncodedBlockRange` implementations must wrap their payloads with `EncodedBlock::encode` or `EncodedBlock::from_length_prefixed`. ([#495](https://github.com/ZcashFoundation/zinder/pull/495))
- The lightwalletd listener now hands `GetBlockRange` response data to HTTP/2 without copying it in the send-stall bound when every chunk keeps at most 512 KiB, and at most twice its own bytes, alive, which holds for every stored Mainnet block so far. A client that stops reading a range stream can therefore keep up to about 2 MiB of stored blocks in memory per stalled stream, instead of up to about 592 KiB of copied buffers. Other methods are unchanged. `zinder-proto` adds `BoundedChunkRetention` and `EncodedBlock::from_length_prefixed_in`; a large message built with `EncodedBlock::from_length_prefixed` is now copied in 64 KiB pieces. ([#501](https://github.com/ZcashFoundation/zinder/pull/501))
- Readers no longer adopt a canonical store replaced at the same path while running when its workload, raw-blob retention, first retained block height, subtree-root coverage mode, or first retained subtree-root index of any shielded pool differs. Earlier releases adopted a replacement with a different first retained block height or subtree-root coverage without a restart. Compact-blocks and light-wallet compatibility now report `schema_mismatch`, and native query and wallet-mode compatibility report `storage_unavailable`, until you restart the reader, which then admits the new store if it meets the reader's requirements. ([#507](https://github.com/ZcashFoundation/zinder/pull/507))
- A `GetBlockRange` response now sends its first frame once it holds 8 KiB of blocks, so behind a gateway that forwards whole HTTP/2 frames a wallet receives the first block in the first round trip of a connection that has been idle, unless the blocks in that frame are large enough to need more than one round trip on their own. Response bytes and later frames are unchanged. ([#521](https://github.com/ZcashFoundation/zinder/pull/521))
- Looking up a mined transaction by ID, as `GetTransaction` does, now reads the transaction's location from canonical storage once instead of twice. Responses are unchanged. ([#523](https://github.com/ZcashFoundation/zinder/pull/523))
- A fresh wallet build's sorters that end with at most 64 runs now merge them while the build reads them, instead of writing a merged run to disk first. A full Testnet wallet build finished about 11% sooner and needed half the peak temporary files for its address sorts. The temporary-file limits refuse a build at the same settings as before, and the published wallet is unchanged. ([#524](https://github.com/ZcashFoundation/zinder/pull/524))
- First sync and live ingest now parse each block once. Transaction identifiers come from the block parse instead of a second parse of every version 5 and 6 transaction, and transaction byte ranges are recorded during the parse instead of serializing each transaction again. On a dense Mainnet range at four cores, time to READY fell by about 40% in local tests. Stored data is unchanged, and no operator action is needed. ([#529](https://github.com/ZcashFoundation/zinder/pull/529))

### Fixed

- Wallet and compact-blocks listeners with a signed settled-history catalog no longer queue `GetBlockRange` requests that select transparent data, or any pool set other than the default shielded projection, behind signed-read permits. These requests read canonical storage immediately with the normal chunk budget. ([#506](https://github.com/ZcashFoundation/zinder/pull/506))
- Listeners whose signed settled-history catalog starts above height 1 no longer queue default shielded `GetBlockRange` requests for heights below the catalog behind signed-read permits. Those requests read canonical storage immediately with the normal chunk budget. ([#509](https://github.com/ZcashFoundation/zinder/pull/509))
- A descending `GetBlockRange` that overlaps the signed settled-history catalog but cannot read signed segments, such as one that runs from inside the catalog to below it, no longer waits for a signed-read permit. It reads canonical storage immediately with the normal chunk budget. ([#511](https://github.com/ZcashFoundation/zinder/pull/511))
- Docker builds that reuse a Cargo target cache now recompile every Zinder workspace crate from the tree being built. Before, a build of a source tree whose files carried older modification times, such as one extracted from `git archive` or a tarball, could reuse another tree's compiled Zinder crates and produce a binary that reported the new commit but ran some old code. The `zinder-ingest-live-tests` image now builds with Rust 1.100 again. ([#513](https://github.com/ZcashFoundation/zinder/pull/513))

### Security

- Public gRPC listeners in zinder-query, zinder-compat-lightwalletd, and zinder-explorer now close a connection after the server has reset 1,024 of its streams because of the client's protocol errors. Previously there was no limit. ([#517](https://github.com/ZcashFoundation/zinder/pull/517))


## [0.23.0] - 2026-11-23

### Added

- Operators can use zinder-projector to back up the canonical and wallet stores together, verify the backup offline, and restore both stores into a fresh directory while preserving cursor history. Keep the archive private and retain its manifest digest separately for recovery. ([#440](https://github.com/ZcashFoundation/zinder/pull/440))
- Operators can repeat a shielded Zingo and Zallet payment on independent Regtest chains and compare wallet behavior against a versioned release baseline. ([#444](https://github.com/ZcashFoundation/zinder/pull/444))
- Release operators can compare a candidate archive against the established wallet payment baseline on two isolated Regtest chains. ([#445](https://github.com/ZcashFoundation/zinder/pull/445))
- Operators can verify that Zingo CLI and Zallet recover shielded Regtest payments after a disconnect or shallow rollback, and compare the observed balances, fees, and spendability with the release baseline. ([#449](https://github.com/ZcashFoundation/zinder/pull/449))
- Wallet-load benchmark reports record the tip before and after a run and a digest that preserves how reads were distributed across wallets. Operators can check the served tip and workload before comparing latency. ([#447](https://github.com/ZcashFoundation/zinder/pull/447))
- Wallet operators can serve settled shielded block ranges from a signed history catalog and require Linux fs-verity for segment reads. Wallet clients use the same lightwalletd endpoint. ([#450](https://github.com/ZcashFoundation/zinder/pull/450))
- Operators can opt in to a faster Pasta field-arithmetic backend at build time (`--build-arg ZINDER_PASTA_ASM=1`, or `--features pasta_curves/asm`). The x86-64 backend needs BMI2 and ADX and the binaries refuse to start on a host that lacks ADX instead of crashing; the default build keeps the portable backend. ([#452](https://github.com/ZcashFoundation/zinder/pull/452))
- Operators can compare shielded payments, fees, and spending of received notes for both Zkool address profiles and Cake Wallet’s Zcash engine against Zallet on disposable Regtest chains. ([#454](https://github.com/ZcashFoundation/zinder/pull/454))
- Release operators can verify payments, return spends, and reopened balances between Zingo and the pinned Vizor, zcash-devtool, and Zally wallets on isolated Regtest chains. ([#455](https://github.com/ZcashFoundation/zinder/pull/455))
- Single-host wallet operators can publish signed shielded history as settlement advances. The Compose publisher keeps its signing key private, resumes from a durable checkpoint, and supports key rotation while the wallet endpoint is serving. ([#461](https://github.com/ZcashFoundation/zinder/pull/461))
- Fresh canonical construction can hash note-commitment trees on several threads with `ingest.construction.tree_hashing_workers`. With more workers, construction with `during_construction = true` reaches READY sooner and stores the same rows. Construction checkpoints now also reject an encoding of any tree other than the one appended. ([#482](https://github.com/ZcashFoundation/zinder/pull/482))

### Changed

- Serving warm historical compact block ranges uses less listener CPU. Time to the first block can still vary by wallet workload. ([#446](https://github.com/ZcashFoundation/zinder/pull/446))
- Benchmark report consumers should select their parser by report kind and format version. RocksDB storage lifecycle and canonical fixture replay now emit v5, and raw-blob retention comparison emits v3. Point-reads v2 replaces `stored_checkpoint_height` and `replay_height` with `on_cadence_height` and `off_cadence_height` and updates the matching request labels. Use the `source` label on `zinder_query_tree_state_reads_total` to measure stored versus replayed reads. For READY-time comparisons with archived cold-certified lifecycle runs, select `--canonical-publication-mode cold-certified`. New runs default to `trusted-fresh`. ([#451](https://github.com/ZcashFoundation/zinder/pull/451))

## [0.18.0] - 2026-11-18

### Added

- `zinder-ingest` can now fail over between node endpoints. Configure fallback endpoints as `[node_fallbacks.1]`, `[node_fallbacks.2]`, and so on, or as `ZINDER_NODE_FALLBACKS__1__JSON_RPC_ADDR` and the other `[node]` fields under a position. `[node]` stays position 0, and a single-endpoint deployment behaves and prints its configuration as before, except that `--print-config` and the `canonical_writer_started`, `upstream_health_probe_started`, and `upstream_health_endpoint_unreachable` log events now show every node URL with its user information, query, and fragment replaced by `[REDACTED]`, and a `[node.health]` `/ready` probe that gets no answer within two seconds, or within the poll interval when that is shorter, falls back to `getblockchaininfo` in the same poll instead of waiting out the poll interval. With fallbacks configured, ingest checks every endpoint at startup, including its genesis block, and starts on the first one that passes, without waiting for higher positions once a lower one passes. An endpoint is excluded until restart only when it reports pruned storage, lacks a required capability, answers for another network, or advertises another network-upgrade table. An endpoint that times out, or that was still being checked when ingest started, is checked again while ingest runs. While following the chain, ingest switches between blocks after three consecutive recoveries of one transport class, `node_unreachable` or `stream_disconnected`, or after the active node has reported not ready for five minutes. It prefers an endpoint that holds its visible tip. It switches to an endpoint on another branch only when that branch shares the settled tip, so the switch replaces blocks within the reorg window, and never to an endpoint whose chain differs at or below the settled tip. Ingest does not switch back on its own; a restart starts at `[node]` again. `/readyz` and the ops `ReadinessReport` report `active_node.position` when fallbacks are configured. New metrics: `zinder_ingest_node_endpoint_active{position}`, `zinder_ingest_node_endpoint_state{position,state}`, and `zinder_ingest_node_endpoint_switches_total{from_position,to_position,failure_class}`. New log events: `node_endpoint_admitted`, `node_endpoint_unreachable`, `node_endpoint_excluded`, `node_endpoint_deferred`, `node_endpoint_state_changed`, `node_endpoint_skipped`, `node_endpoint_switched`, and `node_endpoint_switch_unavailable`. `zinder-query`, wallet-mode `zinder-compat-lightwalletd`, and `zinder-explorer` accept and validate the same list, and refuse a fallback list without `[node]`. `zinder-projector` and compact-blocks compatibility read no node and reject the list as they reject `[node]`. The single-volume images route `ZINDER_NODE_FALLBACKS__*` to ingest, query, and the Explorer, never to the projector, accept `ZINDER_NODE_FALLBACKS__<N>__INDEXER_TLS__*_PEM`, and require each fallback's `INDEXER_GRPC_ADDR` in the wallet-serving image. A new Compose overlay, `deploy/docker-compose.node-fallback.yml`, attaches a second node. Every endpoint must advertise exactly the network-upgrade table the store admitted. Construction admits source responses against the largest `max_response_bytes` in the list, so startup refuses a `source_fetch_max_in_flight_bytes` override below it. When upgrading nodes, upgrade the one ingest is not reading from, then the other, then restart ingest. ([#259](https://github.com/ZcashFoundation/zinder/pull/259))
- `zinder-query` and wallet-mode `zinder-compat-lightwalletd` now broadcast transactions through the ordered node list: `[node]` first, then each `[node_fallbacks.N]` endpoint. Each endpoint is verified on first contact before any transaction reaches it, as `[node]` already was. A broadcast moves to the next verified endpoint when one is unreachable, including when its `broadcast_timeout_secs` expires, or rejects the transaction for its consensus branch. Any other answer is returned. After such a move, the endpoint that answered is tried first from then on, with no timed failback; skipping an endpoint that is not verified yet moves nothing. The node probe also moves past a verified endpoint that stops answering, so an idle reader stays ready and its next broadcast pays no timeout. When every verified endpoint is unreachable, the broadcast fails with `NODE_UNAVAILABLE` and readiness is unchanged. With fallbacks, set `broadcast_timeout_secs` on every endpoint well below wallet request deadlines: a fallback does not inherit the value of `[node]` and otherwise waits for its own `request_timeout_secs`. The node-fallback Compose overlay sets 7 seconds for fallback 1. Readers verify every endpoint on the `[node]` health poll interval and ignore a fallback's. Each endpoint is verified on its own schedule, so one that hangs until its request timeout delays neither another endpoint's verification nor the node probe's move past a verified endpoint that stopped answering. An endpoint that timed out may have accepted the transaction. When an earlier endpoint in the same broadcast was unreachable, a later duplicate or queued answer is reported as accepted with the transaction id computed from the submitted bytes, so lightwalletd wallets receive `errorCode` 0 instead of -27 or -25. For the same reason, a broadcast that no endpoint answered fails with the retryable `NODE_UNAVAILABLE` whenever an endpoint was unreachable, even if another endpoint rejected it for its consensus branch. Verification checks a node's activation table through the height after the served tip, the block a broadcast targets, and is repeated as soon as the writer admits a new network-upgrade schedule revision or that height crosses an activation in the writer's schedule or in the node's own table. Every broadcast also checks the node's verified table against the writer's current schedule through that height, so a node that schedules NU7 at 700 while the writer schedules it at 703, or that still schedules NU7 at 700 after the writer moves it to 703, receives no transaction once a broadcast targets height 700. Until the repeat passes, an endpoint whose verified table still agrees keeps its earlier verification for up to one minute from when the reader first sees the new schedule or height, both while the repeat waits on the node and after it is inconclusive, for example because the node has not received the latest block yet, and the reader retries every two seconds. An endpoint that lacks `sendrawtransaction` or advertises a disagreeing activation table is excluded and verified again after a backoff of 30 seconds that doubles up to 5 minutes, instead of at every poll interval. `ServerInfo.node` reports the first verified endpoint in broadcast preference order. New metrics: `zinder_wallet_broadcast_endpoint_attempts_total{position,outcome}`, `zinder_wallet_broadcast_endpoint_state{position,state}`, and `zinder_wallet_broadcast_endpoint_switches_total{from_position,to_position,cause}`. New log events: `wallet_node_excluded`, `broadcast_endpoint_switched`, and `broadcast_reported_accepted_after_unreachable_endpoint`, and `wallet_node_reverification_inconclusive`; `wallet_node_verified` and `wallet_node_verification_failed` now carry the endpoint `position`. `zinder-explorer` still reads only `[node]`. ([#260](https://github.com/ZcashFoundation/zinder/pull/260))
- `zinder-compat-lightwalletd` can now answer the lightwalletd `Ping` load-testing RPC. Set `compat.ping_very_insecure = true`, `ZINDER_COMPAT__PING_VERY_INSECURE=true`, or pass `--ping-very-insecure`, as on lightwalletd. Both serving modes then report the number of `Ping` calls in flight and sleep for the requested interval, as `lightwalletd --ping-very-insecure` does. Each call holds a server task for as long as the client asks, so enable it only while load testing. The setting is off by default, and `Ping` is then refused with `FAILED_PRECONDITION`. ([#284](https://github.com/ZcashFoundation/zinder/pull/284))

### Changed

- `TreeStateAtHeight` and the lightwalletd-compatible `GetTreeState` now serve the tree state at every indexed height from Zinder's own store, and no longer call `z_gettreestate` on the node. A height between stored checkpoints is rebuilt from the nearest checkpoint and the stored compact blocks, and returns the same `finalState` bytes as before. Existing stores need no rebuild, and `wallet.read.tree_state_at_height_v2` is now always advertised. Each wallet-serving process rebuilds at most one tree state per CPU at once. A request that needs a rebuild while every slot is busy fails at once with `RESOURCE_EXHAUSTED` and the new `TREE_STATE_REPLAY_LIMIT_REACHED` reason; clients should retry with backoff. Heights with a stored checkpoint, which include every block followed live, are never refused this way. Two new metrics track the work: `zinder_query_tree_state_replayed_blocks` samples the blocks each rebuild replays, and `zinder_query_tree_state_replay_refusals_total` counts refusals. `zinder-client` reports the refusal as `ErrorReason::TreeStateReplayLimitReached` with `RetryPolicy::RetryWithBackoff`. Dashboards that attributed tree-state latency to node calls should read these instead. Damaged history between checkpoints, such as a missing compact block or a broken parent link, now fails tree-state requests with `STORAGE_UNAVAILABLE` instead of being masked by the node's answer. ([#256](https://github.com/ZcashFoundation/zinder/pull/256))
- `zinder-query` and `zinder-compat-lightwalletd` now stay ready while their Zebra node is unavailable or still syncing, and native query also stays ready while ingest control is unavailable, until `storage.serving_pair_staleness_ceiling_ms` passes. Stored reads, compact-block sync, `GetLightdInfo`, and the trusted-TLS compatibility route keep answering. Only the requests that need the dependency fail: broadcast returns `UNAVAILABLE` with `NODE_UNAVAILABLE`, and native query's mempool methods and unmined `Transaction` lookups return `UNAVAILABLE` with `UPSTREAM_UNREACHABLE` while ingest control is down. While the writer's live mempool hydrates or rebuilds from its node, `MempoolSnapshot` returns `UNAVAILABLE` with `NODE_UNAVAILABLE`, and a `MempoolEvents` subscription replays its retained events and then ends with the same status instead of staying open and silent. Resubscribe from the last delivered cursor with backoff. That ending raises the native contract revision to 9, so a consumer that relies on it requires revision 9, and `zinder-query` and wallet-mode compatibility admit only a revision 9 `zinder-ingest`: upgrade ingest and the readers together. A canonical writer parked by `reorg_window_exceeded` still refuses every request. `/readyz` lists each unhealthy dependency in a new `degraded` array of `{"input", "dependency_cause"}` entries after the top-level `cause`, and wallet-serving readers add `served_epoch_age_seconds`, the time since the writer committed the chain view they serve; the `zinder.v1.ops.ReadinessReport` message gains the matching `degraded` and `served_epoch_age_seconds` fields. Native query no longer reports `node_unavailable`, `upstream_not_ready`, `node_capability_missing`, or `ingest_control_unavailable` as its own cause, and a writer that reports `upstream_not_ready` now appears as that cause under `degraded` instead of `ingest_control_unavailable`. While the writer's live mempool hydrates or rebuilds from its node, native query and wallet-mode compatibility report `ingest_control` with `node_unavailable` and the `stream_disconnected` failure class, even when its own node probe passes, so `ZinderDependencyDegraded` fires when that lasts longer than two minutes. The single-host wallet-serving container no longer restarts while ingest reports `upstream_not_ready`. ### Security

- Public listeners now bound the denial-of-service paths lightwalletd fixed in GHSA-5xg7-x58j-m5vr, GHSA-4wjx-vhhv-vc8c, GHSA-xrx5-jc6q-9h8r, GHSA-p4pq-3cf7-45rv, GHSA-8vh8-6jg3-8f5v, and GHSA-w24w-x7vw-f2w8. On `zinder-compat-lightwalletd`, `zinder-query`, and `zinder-explorer`, a gRPC request larger than 2 MiB now fails with `OUT_OF_RANGE` (it was 4 MiB), and each process receives at most 32 requests at once per pool, shared fairly across connections; a request over the limit fails with `UNAVAILABLE`, and one that has not arrived within 20 seconds fails with `DEADLINE_EXCEEDED`. Client-streaming calls, such as `GetTaddressBalanceStream` and gRPC reflection, draw on a separate pool and fail with `DEADLINE_EXCEEDED` after 20 seconds without a message. A response whose client stops reading for 60 seconds ends with `DEADLINE_EXCEEDED`. Requests whose list fields hold far more elements than any handler accepts fail with `INVALID_ARGUMENT` before they are decoded. Broadcasts share a 16 MiB transaction budget per process; a broadcast over it fails with `UNAVAILABLE` and the new `BROADCAST_BUDGET_EXHAUSTED` reason, which `zinder-client` retries. The ops endpoint and the Cipherscan REST adapter now enforce header, body, and write-stall deadlines and a connection cap. Keep the ops endpoint on loopback or a private network, and limit concurrent connections per client at your proxy, because many connections can still fill a pool. Several sorters spill at once, so keep about 130 GB free on the volume when a Mainnet wallet construction starts. When the setting is too small, `zinder-projector` now usually stops during the canonical scan instead of after it, with an error that names the setting and its environment variable. A refusal before a sorter has seen all of its records gives only a lower bound, so unset the setting or raise it well above that figure. Explicitly configured values are unchanged. ([#164](https://github.com/ZcashFoundation/zinder/pull/164))
- A `zinder-projector` that crashes or is killed during wallet construction now resumes as soon as it restarts with the same `projector.build_owner_hex`. Previously its leftover construction leases refused the restart for up to `projector.lease_duration_seconds`. A projector with a different owner value is still refused until the lease expires, and the error now names the owner that holds the build; the initial-sync runbook describes how to recover. A second projector running against the same wallet path is refused while the first builds, even with the same owner value, and a crash before the wallet store is created no longer blocks the next build. ([#167](https://github.com/ZcashFoundation/zinder/pull/167))
- `zinder-ingest` now stops within the wallet-serving supervisor's 20-second grace window when it is terminated while fresh canonical construction streams blocks. SST finalization and publication cannot be interrupted, so ingest finishes them before it exits. Construction stops without admitting a store, and the next start rebuilds it, or installs a staged READY store when publication had already finished. During construction, ingest no longer logs `mempool_durable_replay_failed` or `mempool_event_retention_failed` with `DeadlineExceeded`, because the mempool owner and mempool-event retention now start only after the writer admits a READY store. ([#168](https://github.com/ZcashFoundation/zinder/pull/168))
- Explorer views now publish the transparent-address ranking, so `ExplorerQuery.ServerInfo` advertises `explorer.transparent_address.activity_v2` and `explorer.transparent_address.ranking_v1`, and `TransparentAddressActivity` returns address summaries. A fresh Explorer views build includes the ranking from genesis. A store built by Zinder 0.10.0 needs no rebuild: after the upgrade, `zinder-ingest` builds the ranking from canonical history while the other views keep following the tip, logs `transparent_address_ranking_activated` when it serves, and resumes the build after a restart. ([#170](https://github.com/ZcashFoundation/zinder/pull/170))
- A new block no longer makes wallet serving briefly not ready. `zinder-ingest` keeps answering live mempool reads at the previous tip while it rebuilds the mempool view for the new one, so `MempoolSnapshot` no longer fails with "live mempool index is hydrating" after each block, and neither ingest (`syncing`) nor `zinder-query` (`ingest_control_unavailable`) withdraws readiness. A mempool read at the new tip waits up to five seconds for the rebuilt view. Ingest still reports `syncing` when its mempool view trails the canonical tip for 30 seconds. `zinder-query` and `zinder-compat-lightwalletd` also keep publishing new serving pairs while a long request, such as a transparent unspent-output read for an address with millions of outputs, holds an older one, so the reader no longer stalls at `replica_lagging` until a restart. ([#172](https://github.com/ZcashFoundation/zinder/pull/172))

Upgrade notes: the native contract revision is now 6, and native query and ingest must run the same revision. The new client reports a `NOT_FOUND` from an older server as `IndexerError::TransactionAbsenceUnverified` instead of `NotFound`, so upgrade servers before relying on absences; an older client keeps reading every `NOT_FOUND` as `NotFound`. ([#126](https://github.com/ZcashFoundation/zinder/pull/126))
- Compact-blocks `GetBlockRange` now omits transactions that the requested pool types leave with no data, such as a transparent-only coinbase under the default shielded selection, so range responses match lightwalletd.
