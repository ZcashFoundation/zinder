# ADR-0002: Use Boundary-Specific Serialization

| Field | Value |
| ----- | ----- |
| Status | Accepted |
| Product | Zinder |
| Domain | Storage and serialization |
| Related | [Storage backend](../architecture/storage-backend.md), [Public interfaces](../architecture/public-interfaces.md), [Service boundaries](../architecture/service-boundaries.md) |

## Context

Zinder has several serialization boundaries with different failure modes:

- Ordered RocksDB keys must preserve lexicographic order for range reads.
- Canonical chain values must decode within explicit bounds and fail closed on truncated, oversized, or unknown-version bytes.
- Compact-block facts must serve both native WalletQuery and lightwalletd-compatible protocols without making either wire schema canonical.
- Durable control records must bind store identity exactly, and a reader must reject an unsupported layout version without mutating the store.
- Internal Rust-only binary values should optimize for low ceremony.
- Cursor tokens must be stable, opaque to clients, small enough for gRPC metadata, and fail closed on tampering.

A single serializer either weakens ordered keys and cursors or forces Zcash protocol payloads through an unnecessary Zinder-only representation.

## Decision

Zinder uses **boundary-specific serialization**:

1. **Ordered RocksDB keys:** fixed big-endian byte layouts owned by `zinder-store`.
2. **Canonical chain values and control records:** fixed, versioned binary layouts owned by `zinder-store`, such as the ready control record, the construction manifest, chain epochs, chain events, block headers, direct indexes, tree-state checkpoints, and `CanonicalBlockReplayEnvelope`.
3. **Protocol payload bytes:** protobuf bytes generated by `prost` from vendored lightwalletd and native Zinder `.proto` files at RPC boundaries. Compact-block values are the one canonical chain family stored as a protocol message.
4. **Variable-shape storage records:** storage-specific protobuf messages generated by `prost`, kept separate from RPC messages, such as retained mempool event records and materialized-view consumer rows.
5. **Internal binary:** `postcard` for Rust-owned, non-durable internal binary.
6. **Cursor encoding:** fixed `StreamCursorTokenV1` binary layout, authenticated, then base64url encoded.
7. **Materialized-view caches:** no canonical format. `rkyv` is gated behind real workload evidence and stays private to materialized-view stores or caches.

A general serializer is forbidden for ordered store keys and cursor framing. Those bytes are protocol surfaces, not convenience structs.

Each `CompactBlockArtifact` stores structured block identity, time, chain
metadata, and ordered wallet-scan transaction facts. `zinder-store` persists
that model as the native `zinder.v1.wallet.CompactBlock` protobuf message and
validates it into a `CompactBlockArtifact` on every read. Changing that
message's fields or their semantic interpretation is therefore a storage
migration as well as a protocol change. The vendored lightwalletd messages stay
a separate translation and never become a storage format.

## Rationale

Fixed layouts fit boundaries where the byte layout is the contract. RocksDB keys need byte order to match logical network and height order. Cursor tokens need a stable parser, a small fixed surface, and authentication before any server-side seek. Canonical chain values need explicit version bytes, bounded parsing, and exact rejection of truncated or trailing input.

Protobuf fits boundaries where Zinder already speaks protobuf or needs
long-lived durable schema evolution. The native compact-block message carries
the consumer-neutral compact-block model, and the compatibility adapter
translates it independently. Protobuf gives variable-shape storage records a
field-number evolution model and cross-language repair tooling. Reserialized
protobuf bytes are not canonical for semantic hashes, ordered keys, or cursor
payloads.

`postcard` fits Rust-owned internal binary because it is compact, ergonomic, and stable at the wire-format level. It is not the default for durable control records because it is not self-describing and structural compatibility stays project-owned.

`rkyv` is valuable but only after profiling proves a derived-read workload needs it. Its zero-copy access model introduces alignment, validation, tight-buffer, format-control, and migration constraints too high-risk for the canonical store.

## Storage Layout

`zinder-store` owns canonical key, value, and control-record formats. Other crates depend on domain methods, not ad-hoc byte parsing.

Fixed-layout types:

- `StoreKey`: ordered RocksDB key family with explicit network and height encoding.
- Canonical chain values: one fixed layout per chain column family, each with an explicit format version, decoded with exact length checks.
- `StreamCursorTokenV1`: fixed cursor body plus authentication tag.

Cursor body:

```rust
struct StreamCursorTokenV1 {
    cursor_schema_version: u8,
    network_id: u32,
    event_sequence: u64,
    last_height: u32,
    last_hash: [u8; 32],
    flags: u8,
    auth_tag: [u8; 32],
}
```

The cursor body uses `event_sequence` (see [Chain events](../architecture/chain-events.md)) because retained chain-event history is keyed by event sequence. The authentication tag covers every preceding byte. The store uses HMAC-SHA256 with a per-store cursor authentication key so cursors fail closed when tampered with or replayed against another store.

Storage-specific protobuf messages follow protobuf storage discipline:

- Storage messages are separate from RPC messages.
- Native storage messages may reuse deleted tags only in an explicitly breaking
  storage-layout change that rebuilds incompatible data.
- Vendored compatibility messages retain their upstream tag and reservation
  rules.
- Required fields are avoided.
- Enums use explicit unspecified values.
- Migration fixtures are added before changing durable message shapes.

Names reflect domain concepts: `StoreKey`, `CanonicalBlockReplayEnvelope`, `StreamCursorTokenV1`. Names like `key_codec`, `cursor_helper`, `bytes_utils`, or `record` are forbidden.

## Consequences

Positive:

- Native and compatibility protocols share one structured compact-block model, and the compatibility wire schema never becomes a storage format.
- Store keys and cursor tokens stay small, explicit, and testable with golden byte fixtures.
- Variable-shape storage records get protobuf's mature schema-evolution model, while control records stay exact fixed layouts.
- Rust-only internals keep a low-friction `postcard` path without making it a storage contract.
- Future zero-copy work can target derived caches without forcing `rkyv` into canonical storage.

Negative:

- Contributors learn more than one binary boundary.
- `zinder-store` implements and tests fixed-layout parsers instead of deriving everything.
- Fixed chain values and the cursor token need explicit golden fixtures and malformed-input tests.

Neutral:

- `musli` and `wincode` remain on the watch list.
- `bitcode` can remain a benchmark reference, but not a durable-storage candidate.
- FlatBuffers and Cap'n Proto remain options only if Zinder later needs a second IDL for cross-language zero-copy data.

## Switch Criteria

Replacing protobuf storage records with `postcard` requires all of:

- The records are proven Rust-only and low-change.
- Explicit version wrappers and golden fixtures define the current reader and reject mismatched formats.
- The switch materially reduces implementation complexity without weakening repair tooling.

Unlocking `rkyv` for a materialized-view store requires all of:

- A real field-access workload improves P99 latency by at least 30%.
- RocksDB byte access satisfies rkyv alignment and tight-buffer requirements.
- Validation overhead is included in the benchmark.
- Migration behavior is proven with fixtures.
- `rkyv` archive types stay private to the materialized-view store or cache.

Adopting FlatBuffers or Cap'n Proto requires a new ADR.

## Alternatives Considered

### One Serializer Everywhere

Reduces surface area but degrades at least one boundary. Protobuf is unsuitable for ordered keys or cursor framing. `postcard` is not ideal for durable control records. `rkyv` is too risky as canonical storage. Fixed layouts cannot replace protobuf schema evolution for Zcash-compatible payloads.

### Protobuf Everywhere

Strong for payloads and durable control records, but protobuf serialization is not canonical, does not provide the byte-order control needed for RocksDB keys, and adds framing ambiguity to cursor tokens.

### `postcard` for Storage Control Records

Good Rust DX and stable wire format, but not self-describing. Durable control records need a stronger evolution and repair story than compactness alone.

### `rkyv` for Canonical Storage

Excellent for zero-copy field access, but canonical storage needs long-term compatibility, validated reads from RocksDB values, and clear migration semantics. Those requirements are unproven for Zinder's storage shape.

### FlatBuffers or Cap'n Proto

Both are credible zero-copy formats. They add a second IDL while Zinder already needs protobuf for lightwalletd compatibility. FlatBuffers Rust support remains documented as experimental. Cap'n Proto adds its own RPC model, canonicalization concepts, and traversal-limit security surface. Neither is justified.
