# ADR-0016: Wallet-serving readiness follows the serving pair

Status: Accepted

## Context

A wallet reader answers almost every request from its published serving pair. Only a few requests call anything else: a transaction broadcast and the lightwalletd `GetStandardFee` call the node, and mempool reads and lookups of unmined transactions call ingest control. Compact-blocks compatibility serving calls neither. Light-wallet compatibility serving also sends transparent address reads, and transaction lookups when the store keeps no transaction bodies, to the node ([ADR-0023](0023-deployment-profiles.md)).

If readiness required the node and ingest control as well as the pair, any node outage or syncing node would refuse every stored read without making any request succeed. Deployment tooling would spread the outage further. A proxy that checks `/readyz` before each request would close the public route, and Kubernetes or PaaS health probes would restart a serving container even though stored reads stay valid.

The Explorer and the Cipherscan adapter already keep serving through upstream outages for the same reason.

## Decision

1. **The serving pair alone admits traffic.** For native query and compatibility wallet serving, admission is the published canonical-and-wallet pair. For compact-blocks serving, it is the published canonical generation. For light-wallet serving, it is the published canonical generation at a fence the writer attests, with an upgrade schedule the writer attests. Every rule that guards the served chain still refuses traffic; [Readiness](../reference/readiness.md#wallet-serving-readers) lists them.
2. **Dependency health is separate from writer attestation.** A node or ingest-control dependency failure appears under `degraded`. Loss of writer attestation closes the traffic gate when the staleness ceiling passes (decision 5). A parked writer's halt refuses traffic from any input.
3. **Each request fails on its own.** An admitted request that needs the node attempts it independently of readiness probes. When no verified node answers, the request fails with `UNAVAILABLE` and `NODE_UNAVAILABLE`. Local overload, a failed endpoint verification, and a node that answers but refuses each have their own errors ([ADR-0003](0003-epoch-bound-reads-and-storage-roles.md) decision 7). A mempool request fails when ingest control does not answer. A probe observation can be up to a poll interval old, and request timeouts already bound each call.
4. **Mempool streams end while the writer's mempool waits on the node.** `MempoolEvents` replays retained events and then ends with `NODE_UNAVAILABLE` instead of staying silent, because silence reads as an unchanged mempool. An ordinary tip change keeps the stream open for up to 30 seconds while a replacement certifies. After that, the same refusal applies even if the source stays connected. This revised stream semantics in place, so it raised `contract_revision` ([ADR-0013](0013-chain-event-streams.md)).
5. **Losing ingest control is bounded by the staleness ceiling.** Without writer status, the reader keeps serving only until the staleness ceiling passes, because an unattested fence is a question about the served chain, not about a dependency.
6. **A halt seen through ingest control is sticky.** The pair publisher adopts it and refuses traffic. It reopens only after a writer status shows a writer that follows its node with a confirmed tip and attests the pair's fence.
7. **Readiness reports staleness.** The report and metrics carry `served_epoch_age_seconds`, the time since the writer committed the served epoch. `/readyz` answers 200 while the runtime admits traffic, whatever its dependencies report. Operators alert on served-epoch age and on degraded dependencies, not on a reader's 503.
8. **Lightwalletd tip calls carry the network height and refuse a stale tip.** The lightwalletd protocol has no field for the age of the served chain, so the compatibility runtime signals it through the tip calls its clients already check. `GetLightdInfo.estimatedHeight` is the height Zebra would estimate from the served tip, which keeps rising while the tip stands still. `GetLatestBlock` and `GetLightdInfo` fail with `UNAVAILABLE` once the served tip is older than `compat.stale_tip_limit_ms`, 25 minutes by default, counted from its block time or from when the process first served it, whichever is earlier, and the writer cannot vouch that the served tip is the network's tip, because the node is unreachable, reports that its peers show it behind the network, or has a newer block than the writer, the writer is starting or parked, or ingest control does not answer. A tip a reachable, in-sync node still reports is the chain tip however old it is, so a quiet chain keeps answering, as lightwalletd answers while its node is up. The vouching comes from the writer's status on ingest control, which carries the node's committed tip while the writer reaches its node. The stale-tip check applies only to those two calls and leaves readiness unchanged. [Lightwalletd compatibility](../reference/lightwalletd-compatibility.md#stale-tip) lists how each wallet engine reacts.
9. **The `zinder serve` supervisor separates T=0 liveness (`/healthz`) from aggregated readiness (`/readyz`).** `/healthz` returns HTTP 200 immediately so multi-hour canonical or wallet builds never trigger premature orchestrator restarts, while `/readyz` returns HTTP 503 until every required child role reports ready. Node outages leave ingest retrying and readers serving stored data with `node_source` under `degraded`; the supervisor drains children cleanly and exits `0` on `SIGTERM` / `SIGINT`, and drains siblings and exits non-zero only on an unexpected child process exit, removing brittle wall-clock restart timers.
10. **gRPC health reports the same admission.** The native and lightwalletd listeners serve `grpc.health.v1.Health` from the readiness state `/readyz` reads, with no second model, so `SERVING` means `/readyz` answers 200 and a degraded dependency does not change it. Health and gRPC reflection stay outside the traffic gate. Shutdown publishes `shutting_down` before the listener drains, so `/readyz` and health turn to `NOT_SERVING` together. [gRPC health](../reference/readiness.md#grpc-health) describes the service.

[Readiness](../reference/readiness.md#readiness-causes) lists the causes and report fields. [Service operations](../architecture/service-operations.md#recovery) describes recovery.

## Evidence

- Decision 1, readiness without checkpoint coverage: judgment. Admission answers whether the served chain is correct, and a store between checkpoints still answers every tree-state read correctly by replay. Its cost is restore latency on stores that are not yet dense, measured in the consequences. A decision on [#500](https://github.com/ZcashFoundation/zinder/issues/500) to report coverage reopens it.
- Decision 1, light-wallet admission: judgment. Light-wallet serving has no wallet store to pair, so it admits the canonical generation as compact-blocks serving does. It also requires the writer to attest the upgrade schedule, because each forwarding node endpoint is checked against that schedule.
- Decision 1, an open traffic gate while the light-wallet node is down: measured. With the node stopped under load on Regtest, local block ranges, tree states, and subtree roots kept serving byte-identical payloads and shielded scans completed, while 0 of 16 transaction enhancements succeeded ([#475](https://github.com/ZcashFoundation/zinder/issues/475)). A decision on [#475](https://github.com/ZcashFoundation/zinder/issues/475) to report node-backed methods separately for routing reopens it.
- Decisions 2, 5, and 8: judgment. The staleness ceiling limits how long a reader can serve a fence the writer no longer attests. The stale-tip check limits what the tip calls report while preserving admission for requests that can use the stored data.
- Decision 3: judgment. A probe observation can be stale, and request timeouts already bound each call, as the alternatives explain. The revision names the error classes the code returns.

## Consequences

- Through a node outage, a syncing node, or an ingest-control outage within the staleness ceiling, readers keep serving stored data, as [Readiness](../reference/readiness.md#during-a-node-outage) lists. Wallets keep scanning.
- Broadcast fails per request while none of a reader's node endpoints answers. A load balancer keeps routing to such a reader, and nothing steers a broadcast to another reader.
- A light-wallet reader has two separate dependencies. Losing the forwarding node fails only the calls that need it, including broadcast, which is rejected rather than queued, and an address-history stream can fail after delivering rows. Retained mined bodies and empty unspent-output requests still resolve locally. Mempool methods depend on ingest, not on the forwarding node (decision 4). The tip calls refuse only when the served tip is stale and no writer witness vouches for it (decision 8). Block ranges, tree states, and subtree roots keep serving while the writer's attestation holds, so a shielded scan can complete, but a completed scan does not show that the wallet can display or spend its funds. `/readyz` stays 200, `node_source` appears under `degraded` once a probe completes and fails, and readiness has no separate signal for node-backed methods. [Readiness](../reference/readiness.md#during-a-node-outage) lists the behavior per method.
- During a node outage, lightwalletd wallets see `estimatedHeight` pull away from the served tip, and once the tip is 25 minutes old their tip calls fail, so they stop syncing and report the server unreachable instead of building transactions on a tip that has stopped. Wallets expire transactions 40 blocks after the tip they were told, 120 from NU7, which is 50 minutes of target time, so the default leaves half that window as margin.
- A wallet that cannot reach the tip calls stops syncing even though block ranges and tree states still answer. A private deployment that prefers to keep its wallets syncing through a long outage sets `compat.stale_tip_limit_ms` to 0, and its wallets then build transactions that expire on arrival once the tip is about 50 minutes old.
- A writer behind its node, catching up or restored from an old snapshot, also refuses the tip calls until its tip is within the limit or matches the node's, while `/readyz` reports it ready.
- On a quiet chain, Regtest included, the reachable node vouches for the tip, so the limit needs no per-network default. A Regtest node without peers whose `/ready` check is enforced on test networks reports `insufficient peers` and does not vouch.
- A node that answers but reports that its peers show it behind the network (Zebra's `syncing`, `insufficient peers`, or `no tip`) does not vouch for its tip, so the tip calls refuse an old tip there too. Not-ready reports computed from the tip's age (`tip_age`, `lag`, and the JSON-RPC fallback's) are ignored, because a quiet chain raises them too. Go lightwalletd keeps answering in that state, but a wallet shown that tip builds transactions that expire on arrival, and every engine in the compatibility evidence recovers from `UNAVAILABLE` on the tip calls.
- Native clients are unaffected: every native response carries the chain epoch, whose age they read.
- Native query never reports a node or ingest-control cause as its own. Those causes appear only under `degraded`.
- Wallet-mode compatibility admits ingest control at startup, so it fails to start against an ingest of another network or contract revision.
- An ingest restart during a node outage leaves readers refusing, because ingest needs the node to open its store and confirm its tip.
- READY does not imply restore capacity. The readiness rule in decision 1 does not consider tree-state checkpoint coverage, so a store with a checkpoint every 100 blocks reports READY while a fresh reader replays up to 99 blocks for each tree-state request between checkpoints. On Mainnet, 16 concurrent wallet restores over a dense historical window took about 62 seconds for their first period on such a store, against about 5.5 seconds with a checkpoint at every block ([#500](https://github.com/ZcashFoundation/zinder/issues/500)). Such stores include stores built before the dense construction default and carried forward by an upgrade within a compatible schema, and stores built with Explorer coverage, until the background pass densifies them. Operators follow that pass through `zinder_ingest_tree_state_densification_watermark_height` and `zinder_ingest_tree_state_densification_remaining_strides`, and the share of tree-state reads answered from stored checkpoints through the `source` label of `zinder_query_tree_state_reads_total` ([Metrics](../reference/metrics.md)). Whether readiness reports incomplete coverage under `degraded` is not decided ([#500](https://github.com/ZcashFoundation/zinder/issues/500)).

## Alternatives rejected

- **Keep readiness as the conjunction of every input.** It refuses every stored read without making any request succeed.
- **Close the light-wallet traffic gate while its node is down.** Shielded scanning needs no node, so closing the gate would refuse the profile's main workload while it still succeeds.
- **A new traffic-admitting cause such as `serving_degraded`.** It would compete with `serving_pair_stale` for the single cause slot and add an enum value consumers must learn. A separate list composes with every cause.
- **Fail node-backed requests fast while the probe reports an outage.** The observation can be stale, and the request timeout already bounds the call.
- **Serve indefinitely without ingest control.** The staleness ceiling bounds how long a reader serves an unattested fence, whatever the reason.
- **Let node-outage timers kill healthy serving containers.** Restarting during a node outage turns a degraded dependency into a total outage because ingest requires a reachable node to open; `zinder serve` restarts only on unexpected child exits.
- **Keep `estimatedHeight` equal to the served tip.** No wallet's stale-server check can fire, and a wallet on a stopped tip builds transactions that expire on arrival.
- **Pass the node's own estimate through ingest control.** The node computes it with the same estimator from its own tip, so while the served tip follows the node the value does not change, and during an outage there is no node estimate to read.
- **Fail only `GetLatestBlock`.** The ZODL iOS SDK ranks servers by `GetLightdInfo` alone, so a stale server would keep ranking first.
- **Treat every `upstream_not_ready` report as behind.** Zebra's `tip_age` and `lag` reports and the JSON-RPC fallback's are computed from the tip's age, so a quiet Mainnet or Testnet chain would raise them and refuse the tip calls of every server serving the true tip.
- **Refuse on tip age alone.** Testnet often goes longer than 25 minutes without a block, and Mainnet miners occasionally stall, so every server of a quiet chain would refuse at once while it serves the true tip.
- **A limit counted in blocks.** NU7 shortens blocks to 25 seconds while the default expiry stays 50 minutes, so a block count would shrink the margin threefold.
- **Bound `upstream_not_ready` the same way.** A node that answers with its sync state rules out a stuck client, so a restart during a long resync only turns a serving container into a full outage.
