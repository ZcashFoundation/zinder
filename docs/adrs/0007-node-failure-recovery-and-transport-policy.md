# ADR-0007: Recover from node failures in ingest and own transport policy per upstream

Status: Accepted

## Context

Nodes restart, stall, and fall behind. Ingest must survive those failures. Storage and integrity failures must still stop the process, and a reorg deeper than the window must stop following, because retrying them could hide an unsafe state.

Long-lived connections also fail silently. In two production incidents, an internal gRPC channel hung for hours after one HTTP/2 protocol error, and ingest's JSON-RPC client reported the node unavailable for 12 hours while the node was reachable; a restart fixed both. Keep-alive alone does not cure this: the JSON-RPC library exposes no connection-pool settings, and HTTP/2 pings sent while idle make some gRPC servers close the connection.

Public listeners accept clients Zinder does not control. Slow or oversized requests can exhaust server resources.

## Decision

1. **Ingest owns recovery.** Source adapters describe a failure with a failure class and reason. Ingest decides. While following, every source failure drains ingest readiness and retries from durable state with a backoff chosen by class. During fresh construction, once a transport-class or node-not-ready failure outlasts its bounded retries, ingest switches to a qualifying standby under decision 5 (ratified; implementation tracked in [#302](https://github.com/ZcashFoundation/zinder/issues/302)) and exits only when failover is ineligible or no qualifying standby is available; a restart then begins construction again. A storage or integrity failure exits the process, except damage that the background tree-state verification finds in stored history, which ingest reports to its readers and parks readiness on instead ([ADR-0014](0014-consumer-neutral-wallet-data-plane.md)). A replacement deeper than the reorg window parks the writer, which stays up and refuses wallet traffic ([ADR-0010](0010-reorg-window-and-displaced-blocks.md)).
2. **Readiness carries the detail.** Ingest readiness reports the failure class, the latest reason, the consecutive failure count, and the outage duration.
3. **Retries happen at one level.** During fresh construction, a call retries only transport failures. While following, each call makes one attempt, and the loop re-observes the node before it issues dependent requests.
4. **Only the writer drains.** Wallet-serving readers stay ready during a node outage, report the node as a degraded dependency, and fail only the requests that need the node ([ADR-0016](0016-wallet-serving-readiness.md)).
5. **Ingest fails over across an ordered node list during both live following and fresh construction ([#302](https://github.com/ZcashFoundation/zinder/issues/302)).** With `[node_fallbacks.N]` configured, ingest switches endpoints only on transport-class failures or a node that stays not ready (during fresh construction, after bounded retries; implementation pending under [#302](https://github.com/ZcashFoundation/zinder/issues/302)). Malformed data, protocol mismatches, and other failure classes never trigger a switch, because switching would pick whichever node's answer parses and could hide a Zinder defect. Every candidate must agree with the store's network and admitted activation table ([ADR-0008](0008-consensus-parameters-from-the-node.md)). Live-follow candidates remain subject to Decision 11 and [ADR-0006](0006-node-source-boundary.md) Decision 9's continuous pruned-validator recovery-interval checks rather than an archive-only requirement. Canonical construction failover additionally requires an archive standby (`pruned: false`) whose chain contains construction's fixed target `build_tip` by exact hash before resuming from the lowest uncommitted height inside the single unpublished staging run ([ADR-0009](0009-ingest-lifecycle-and-construction.md)). There is no timed failback.
6. **Each upstream has one transport owner.** `zinder-runtime` builds every internal Zinder gRPC channel, and `zinder-source` builds every node client. A compatibility service may own a narrow transport module for an external product it calls, and so may the benchmark load client, which calls lightwalletd servers outside Zinder and sends them no keep-alive pings. A structural test refuses client construction anywhere else.
7. **Transport policy is constants, not configuration.** Internal channels ping while idle because both ends are Zinder. Node-facing channels do not, because the node's server policy is outside Zinder's control. An internal dial gives up after 5 seconds by default. The bound covers the name lookup, the TCP connect, the TLS handshake, and the peer's whole initial HTTP/2 `SETTINGS` frame, because the HTTP/2 client handshake completes before the peer sends a frame. Every HTTP/2 peer, a proxy included, opens its side of the connection with that frame, so the dial sends no request and needs no route or credential at a proxy. A peer that drops packets, or accepts the connection and then stays silent or stops partway through that frame, therefore cannot hold a caller for the operating system's connect timeout. A peer that opens with any other frame does not speak HTTP/2, and the dial fails at once. Every reconnect the channel makes on its own keeps the same bound, from the name lookup until the peer's `SETTINGS` frame is complete, so a call that waits on a reconnect to a stalled peer fails within it rather than waiting for the keep-alive ping to time out. Zinder runs the client TLS handshake itself rather than through tonic, because tonic does not expose the decrypted stream that carries the peer's frames. Callers that dial on first use share one dial in flight, so concurrent callers wait for one bound rather than one each. A runtime that dials at startup, such as `zinder-projector` and `zinder-compat-cipherscan`, dials again after a dial that times out until one connects or the runtime stops, so a peer that is slow to come up delays startup instead of ending it. A caller that needs another bound passes it to `connect_zinder_grpc_with_timeout`, and a caller that also wraps the dial in a deadline of its own lets the shorter bound end it.
8. **Node clients rebuild themselves and bound their own calls.** After three consecutive transport failures, a node client is replaced with a freshly built one. An HTTP 429 refusal is not a transport failure: the node is up and the connection works, and a fresh client would open more connections to a node that refuses them for having too many. Because the JSON-RPC library exposes no connection-pool limit, the node client admits its calls through a configurable number of slots, `node.max_concurrent_requests`, which defaults below Zebra's connection limit. Readiness probes take a separate slot so a saturated client cannot fail readiness.
9. **Indexer TLS is in-process with file and inline-PEM inputs; public-listener PEM TLS follows the same model under [#300](https://github.com/ZcashFoundation/zinder/issues/300).** Today, upstream node clients negotiate TLS from the indexer URL scheme using `[node.indexer_tls]` (and `[node_fallbacks.N.indexer_tls]`), accepting mutually exclusive `*_path` file references or inline `*_pem` values for trust roots, client certificates/keys, and `server_name`, and rereading file material on each reconnect. Extending this contract to the public gRPC listeners (`zinder-query`, `zinder-compat-lightwalletd`, and `zinder-explorer`) is ratified and pending implementation under [#300](https://github.com/ZcashFoundation/zinder/issues/300): once implemented, opt-in `[query.tls]`, `[compat.tls]`, and `[explorer.tls]` sections will accept mutually exclusive `cert_path`/`cert_pem` and `key_path`/`key_pem` pairs (plus optional `client_ca_path`/`client_ca_pem` on `[query.tls]` for backend mutual TLS) via the shared PEM validation and config redaction contract, reloading file-backed `*_path` material every 60 seconds and on `SIGHUP` via an atomic swap without dropping open streams (retaining the prior valid server configuration on reload errors). Until [#300](https://github.com/ZcashFoundation/zinder/issues/300) lands, public gRPC listeners serve plaintext h2c and reject unknown `[<role>.tls]` fields.
10. **Public listeners share one bounded policy.** `zinder-query`, `zinder-compat-lightwalletd`, and `zinder-explorer` bound streams per connection, the stream resets a client's protocol errors can make the server send on one connection, request message size, requests being received at once, and responses a client stops reading. The limits are constants. A response a client stops reading is abandoned at the send-stall deadline, counted from when the transport last took its data. That stops the call's work once any read already in flight finishes, and resets its HTTP/2 stream with `CANCEL`. The reset frees the data HTTP/2 holds for the response and its place among the connection's streams, while the connection and its other streams stay open. Most gRPC clients report the reset as `CANCELLED`. The listener ends a response, or waits on a producer that has paused, only once h2 has encoded the data already sent. It sends the data's last byte as a frame of its own and waits for h2 to drop it, which h2 does once it has encoded everything queued ahead of it, so a stalled finished or paused response is reset at the deadline like any other. A stream whose data the connection cannot write out within the deadline, on a slow or busy connection, is reset too. The reset is scheduled at the deadline; h2 discards the stream's queued data and frees its slot the next time it writes to the connection, or the write rule below closes a connection that cannot write. Zinder serves the public listeners with its own connection loop because only the task hyper sends a stream from can end that stream, and tonic's server does not let a caller run that task. Under the ratified target contract in [#300](https://github.com/ZcashFoundation/zinder/issues/300) (pending implementation; public listeners currently serve plaintext h2c and require `security.allow_public_bind = true` for non-loopback binds), opt-in listener TLS will run `tokio-rustls` with the explicit `ring` provider inside that connection loop above the socket write-stall wrapper (measuring encrypted socket progress against the 16 KiB write-stall bound, preserving optional PROXY-protocol preface parsing before TLS, enforcing ALPN `h2` or `http/1.1` for gRPC-Web with TLS 1.3 0-RTT early data disabled, capping concurrent handshakes at 128 per listener with a 5-second handshake deadline, and recording peer identity via `TlsConnectInfo`), exempting TLS-enabled public gRPC listeners from `security.allow_public_bind = true` while leaving operational HTTP `/readyz` and `/healthz` checks separate on `[ops]`. Once a write to a connection blocks, the connection must write 16 KiB, or finish writing everything it had buffered, within the send-stall timeout or be closed, because a client that reads less has stopped reading every stream on it, or reads too slowly for a reset to reach them. An HTTP/1.1 connection, which carries one response at a time, is closed when its response stalls. These bounds hold per stream and per connection, and Zinder sets none across the process. The receive limit keeps one client from locking the others out by counting slots per client connection. Behind a proxy, a listener takes that connection from a forwarding header only when the operator sets `trust_proxy_client_address` (which, once [#300](https://github.com/ZcashFoundation/zinder/issues/300) lands, is disallowed when built-in listener TLS serves clients directly or behind PROXY protocol), because any client that reaches the listener directly can set the header. It reads the header only when a request carries it once, as one `ip:port` or bare IP address, so a proxy that appends to a client's header instead of replacing it never passes the client's value on. Clients are never grouped by IP address when the header names a connection, because wallets behind Tor share exit addresses and an `ip:port` keeps each connection apart. A proxy that names only a bare IP, as a load balancer does with `{client_ip_address}`, gives Zinder no port to key, so Zinder groups that whole address as one client. Hosted public endpoints needing ACME, HTTP/3, WAF, or per-client rate limiting keep using the reference NGINX edge proxy in [#245](https://github.com/ZcashFoundation/zinder/issues/245).

11. **Pruned-validator admission is continuous.** For the ratified live-follow extension, ingest applies [ADR-0006](0006-node-source-boundary.md) decision 9 at startup, failover, restart, and throughout following. A missing or insufficient horizon or a gap in the required recovery interval fails closed and parks ingest immediately. With `[node_fallbacks.N]`, every candidate must independently pass the admission checks. Decision 5 still governs which failures trigger a switch.

[Node endpoint failover](../architecture/chain-ingestion.md#node-endpoint-failover) describes switching, [Node source boundary](../architecture/node-source-boundary.md) describes failure classes and indexer TLS, and [Configuration](../reference/configuration.md) lists listener limits and the internal dial bound.

## Evidence

- Decision 10, resetting a stalled stream: external constraint. hyper 1.12 does not poll a response body while that body's last chunk waits for flow-control window, and it gives a service no way to reset the stream, so nothing the send-stall bound returns after the deadline reaches HTTP/2. Ending the stream's task does reach it: h2 0.4.20 then discards the data it queued for the stream, sends `RST_STREAM` with `CANCEL`, and frees the stream's slot. On a real HTTP/2 connection that fills its 200 stream slots with streams it never reads, every stalled stream's data and slot are freed at the deadline while the connection's remaining stream keeps working ([#503](https://github.com/ZcashFoundation/zinder/issues/503)). A hyper API that lets a service reset a stream waiting for window would let the listeners return to tonic's server.
- Decision 10, ending a response only once its data has window: external constraint. hyper 1.12 asks a response body for its next frame as soon as it has queued the previous one, and queues the body's end without waiting for window. Once it has queued the end, h2 0.4.20 keeps the stream and its data until the client grants window, and no reset reaches it. hyper does wait for window before it queues a chunk it holds (`proto::h2::PipeToSendStream`), and h2 grants a stream window only once every byte queued before it fits the peer's window. A one-byte frame held back from the data therefore passes only once everything before it can be sent. Window alone is not enough, because a client can take it back with `SETTINGS` before the data goes out. h2 sends a stream's DATA in order, and it copies a frame this small into its write buffer and drops it as it does (`codec::FramedWrite::buffer`), so the probe's drop shows that everything queued ahead of it was charged to the window and encoded, which no later `SETTINGS` decrease can undo. h2 drops the probe unsent only when it discards the stream's queue for a reset or the connection ends. This is hyper's and h2's behavior, not their API, and the listener's tests fail if an upgrade changes it. On a real connection whose 200 streams have finished or paused while their data waits for window, every stream's data and slot are freed at the deadline.
- Decision 5, construction failover across `[node_fallbacks.N]` ([#302](https://github.com/ZcashFoundation/zinder/issues/302)): Judgment. Rebuilding from genesis after an upstream transport outage wastes completed staging when an operator already supplies verified archive fallbacks (`pruned: false`) carrying construction's exact `build_tip` hash; malformed data and protocol mismatches still fail closed.
- Decisions 9 and 10, built-in opt-in PEM TLS in the public listener connection loop ([#300](https://github.com/ZcashFoundation/zinder/issues/300)): Judgment. Terminating TLS inside the custom connection loop with `ConnectionIo` beneath `tokio-rustls` preserves per-stream `CANCEL` resets and the 16 KiB write-stall bound without pulling ACME, HTTP/3, WAF, or rate limiting into `bin/zinder`.
- Decision 11: Judgment. A validator can prune away blocks after it first qualifies, so admission must protect recovery throughout following. A missing block inside an interval that passed admission reopens the checks. See [#713](https://github.com/ZcashFoundation/zinder/issues/713).

## Consequences

- Once following, ingest stays alive through node outages, and operators see the failure class and outage duration without reading logs.
- With fallback nodes, ingest keeps committing through an outage of its active node. Each switch costs one mempool rebuild, during which ingest readiness is withdrawn.
- A new source error must choose a failure class, and a new node adapter or internal channel adds one factory in the owning transport module.
- Operators rotate indexer client material by replacing the files.
- Operators still limit connections per client address at their proxy, because a client spread over many connections can keep the receive slots full ([Service operations](../architecture/service-operations.md#security-boundary)).
- Zinder maintains the public listeners' connection loop, including the per-request connection address and `grpc-timeout` handling that tonic's server provided.
- An HTTP/2 response that ends after data, or pauses after data for longer than one scheduler turn, sends its last byte of data in a DATA frame of its own. Empty and trailers-only responses, responses over HTTP/1.1, and data that is a single byte add no frame. Over a 90 ms path it added no latency.
- The listener waits one task wake for h2 to encode the probe before it queues END_STREAM, so when the window is exhausted END_STREAM leaves in a TCP segment of its own. Over a 90 ms path that segment followed the probe within 0.06 ms and never waited on an acknowledgement.
- A stream whose connection cannot write its data out within the send-stall timeout, because the socket is slow or busy streams share it, is reset even while the connection meets the 16 KiB write rule.
- A slowly reading client is reset when one piece waits the send-stall timeout for window to cover everything queued ahead of it plus one byte. In the worst case that takes a whole piece of new window, so frequent but small window updates can still end a stream. A client that grants window only for whole messages would leave that frame waiting and be reset as stalled. grpc-go, tonic, and hyper grant window as they read.
- A client that reads its socket a trickle at a time stays within the per-connection memory bound but has no deadline, because HTTP/2 frees a reset stream's data only when it next writes to the connection.

## Alternatives rejected

- **A boolean retry classification.** It cannot separate recoverable source failures from unsafe store states, and it carries no operator detail.
- **Switching nodes on any failure.** It would mask Zinder defects behind whichever node answers in a parseable form.
- **Rebuilding the node client on HTTP 429.** Each rebuild opens new connections to a node that refused one for having too many.
- **Mapping HTTP 429 to `RESOURCE_EXHAUSTED`.** That code tells clients that Zinder's own limit refused them. The node, a dependency, refused the call, so it shares `UNAVAILABLE` with the other node failures under its own reason.
- **Copying the internal keep-alive settings to node clients.** Idle pings can make a node's gRPC server close the connection.
- **Rebuild-on-failure for internal channels.** It would import node failure semantics into every internal service channel.
- **A health-check request on every internal dial.** A proxy that resets unauthenticated streams or drops unknown routes would fail every dial, although it serves the methods Zinder calls.
- **A shorter HTTP/2 keep-alive interval to catch a silent peer.** The first keep-alive ping goes out one interval after the connection opens, so a 5-second bound would set the steady idle cadence to a few seconds.
- **An egress proxy that presents the client certificate.** It adds a component to every deployment that uses the indexer stream, while the client already negotiates TLS in-process.
- **Closing a stalled stream's connection.** It frees the same data, but it ends the connection's other streams, and behind a proxy those belong to other wallets that share the proxy's pooled connection.
- **A connection age limit.** It ends long healthy streams by elapsed time, which no stream is meant to end on.
- **Ending a stalled response with trailers alone.** Its `DEADLINE_EXCEEDED` trailers wait behind the unsent data, so a client that withholds window never receives them, and the data stays.
- **Probing whenever the producer is pending.** A producer that only yields to the scheduler, as `tokio_stream::iter` does every 32 items, would have its frames split, and a wallet behind a gateway that keeps frames would decode a short range's first rows later. The listener waits one turn of its task before it treats a producer as paused.
- **Ending a response once its probe has window.** A client that lowers its window with `SETTINGS` before the data is written strands up to 1 MiB per stream, with its slot, and nothing can reset the stream once its end is queued.
- **Tracking what the socket has written for a stream.** Neither hyper nor h2 exposes it. The capacity check the probe passes through is the only signal either offers.
- **Holding the compat range-stream slot until a response ends.** It would bound the data of streams stalled on window across the process, but it adds a public type to `zinder-runtime`, and a client that trickles its socket would still escape it.
- **Delegating public listener TLS exclusively to tonic's built-in `ServerTlsConfig` ([#300](https://github.com/ZcashFoundation/zinder/issues/300)).** Using tonic's default server transport would give up custom stream-reset executor control (`ResettableStreams`) and require restarts for certificate rotation. Putting ACME, HTTP/3, WAF, or per-IP rate limiting inside `bin/zinder` was likewise rejected in favor of keeping those edge responsibilities in the NGINX reference proxy ([#245](https://github.com/ZcashFoundation/zinder/issues/245)).
- **Discarding all completed staging without failover when `[node_fallbacks.N]` is healthy during construction ([#302](https://github.com/ZcashFoundation/zinder/issues/302)).** Rebuilding from genesis on a single upstream transport failure wastes verified staging when a standby node already matches the store's network, archive completeness, activations, and fixed `build_tip` hash.
- **Scrubbing inline PEM variables out of `/proc/<pid>/environ` or requiring a restart to rotate file-backed TLS certificates.** Mutating process environment variables needs `unsafe` code, which the workspace denies; Zinder accepts redacted inline `*_pem` inputs for single-shot secrets and supports zero-drop reload for file-backed `*_path` TLS material.
- **P2P failover or tip vouching.** An alternate validator admitted under decision 5 preserves the chain authority and epoch checks in [ADR-0006](0006-node-source-boundary.md). A peer answer cannot replace them.

- 2026-11-24. Decision 8 classifies an HTTP 429 node refusal as `node_rate_limited`, which never rebuilds the client, and bounds the JSON-RPC calls a node client has in flight with `node.max_concurrent_requests`, with a separate slot for readiness probes.
- 2026-11-24. Decision 10 accepts a bare IP in the trusted proxy header, as a GCP Global External Application Load Balancer emits with `{client_ip_address}`, and keys that whole address as one client. A connection's `ip:port` still keeps clients that share an exit address apart, so the Tor invariant holds.
- 2026-11-23. Decision 10 states that abandoning a stalled response ends its work but leaves the data HTTP/2 holds for it until the client reads, resets, or disconnects.
- 2026-11-23. Decision 10 resets a stalled response's HTTP/2 stream instead of ending it with `DEADLINE_EXCEEDED` trailers, and ends a response only once the client's window covers its data, learned from a one-byte probe that relies on hyper waiting for window before it queues a chunk it holds. Probing on every pending poll, tracking socket writes, and holding the range-stream slot were rejected. A blocked connection must write 16 KiB within the timeout. `CONTRACT_REVISION` is 15 because the documented outcome of a stalled call changed, although `zinder-client` retries both outcomes with backoff and a client that withheld window never received the old trailers. The end waits until h2 has encoded the probe, so a later `SETTINGS` decrease cannot strand the data; ending once the probe only had window was rejected for that reason.
