# ADR-0014: Wallets read one consumer-neutral data plane from stored artifacts

Status: Accepted

Decision 4 revision. [Stored checkpoint roots for materialized views (#427)](https://github.com/ZcashFoundation/zinder/pull/427).

## Context

A store built close to the node's tip can pass lightwalletd smoke tests and a new-wallet flow, then fail when a wallet asks for history. Recovery, rescan, and imported accounts need tree state at arbitrary anchors, subtree roots from index zero, and transparent outputs created at any height. Zodl and the Android SDK exposed the gap first, but Zallet, full-node wallets, and native Rust applications need the same data.

Two risks pull in opposite directions. Designing around one wallet produces app-specific patches and no durable contract. Becoming lightwalletd makes its wire vocabulary Zinder's identity, when compatibility is only one way in.

Several optional fields, such as a fee that needs resolved inputs or a raw transaction that needs retained blobs, depend on what a deployment stored or wired. A consumer has to tell "absent" from "zero" without guessing.

## Decision

1. **The product boundary is a consumer-neutral wallet data plane.** `zinder-ingest` indexes canonical artifacts once. Native consumers read them through typed, epoch-pinned gRPC or Rust surfaces. `zinder-compat-lightwalletd` is an adapter over the same artifacts and owns no storage, query semantics, or vocabulary. Native method names and errors may differ from lightwalletd's where that serves consumers better. Wallet compatibility is a coverage contract, never an app-specific workaround, and no profile is named after a consumer.
2. **The core contract is fixed.** The data plane serves compact block ranges, tree state at explicit anchors, subtree roots by pool and index, and transparent outputs by address and height. Every read is consistent with one chain epoch. Readiness and artifact availability are reported truthfully.
3. **Wallet-serving coverage is complete history.** A store built for wallet serving keeps all canonical history from height 1. Shielded activation heights cannot bound transparent history, because a transaction at any height can spend an output created earlier. Wallet-serving construction rejects a checkpoint-height override, and ingest refuses an existing store whose retained history starts later than this requires. Following cannot repair omitted history, so the operator rebuilds.
4. **Reads come from stored artifacts only.** A missing artifact is `ARTIFACT_UNAVAILABLE`. Query runtimes never fill a response from the node. Tree state at a height without a stored checkpoint is reconstructed from stored data, and a failed reconstruction is store damage, not a reason to ask the node. A stored checkpoint is served as written: every checkpoint is validated when it is written, including the bulk loader's check that it carries a frontier for exactly the pools active at its height, RocksDB block checksums detect corruption at rest, and a wallet tree-state read checks only the framing of the row's frontiers and does not read its roots. Materialized-view replay can use a stored final root after checking the frontier framing, active pools, and block time. This read returns only roots. Ingest also re-verifies every settled row in the background, reading through no block cache, and reports a failure in `CanonicalControl.WriterStatus` as typed store damage, so readers refuse traffic with `canonical_store_damaged` and ingest readiness parks; [Chain ingestion](../architecture/chain-ingestion.md#tree-state-verification) describes the cycle, the damage record, and how damage clears. A wallet tree-state response cannot seed an accumulator or be written back as a checkpoint. A path that builds or stores tree state from a stored checkpoint, such as a reconstruction or a stride of the densification pass, parses it in full and re-derives its roots first. Concurrent reconstructions are capped, and excess requests are refused instead of queued; [Wallet data plane](../architecture/wallet-data-plane.md#tree-states-and-subtree-roots) gives the cadence and limits.
5. **Optional payload fields use explicit presence.** A field that a deployment may be unable to fill is a proto3 `optional` scalar or a `repeated` field. Absence is never encoded as zero or empty bytes. When absence has more than one cause that a reader would act on differently, the message carries a companion status enum. A named capability string says the field is filled on this deployment.
6. **Capabilities follow evidence.** A capability for an optional field is advertised only when the deployment can fill it, judged from persisted facts. Raw-block and raw-transaction capabilities follow the raw-blob retention the store recorded at construction. Completeness capabilities for materialized views require verified coverage up to the view tip. A runtime advertises one capability set through every discovery surface.

7. **Settled tree states are stored, not replayed.** Under the default selection (`ingest.tree_state_densification.enabled = true`, `selection = "every-block"`), fresh construction stores a tree-state checkpoint for every loaded block directly during the initial pass, so every constructed height through the build tip is a stored read immediately at READY without replaying commitments a second time ([Chain ingestion](../architecture/chain-ingestion.md#tree-state-densification)). Its full Mainnet construction and storage cost is estimated and not yet qualified. An operator who needs less storage or faster initial readiness can disable densification or choose the `commitment-budget` selection, which keeps construction sparse (every 100 blocks and at the build tip); under `commitment-budget`, the background pass then stores a checkpoint each time 1,024 note commitments have accumulated by default, bounding every replay to fewer than 1,024 commitments for a small fraction of the storage. That option must be selected before the first start that runs the `every-block` default: switching afterwards keeps every stored row, because a dense stride already satisfies the looser budget and the writer only inserts missing rows, so the switch changes only the work still outstanding. Once the writer follows the tip, the background pass checks whether each settled 100-block stride meets the selected coverage. Under `every-block`, it checks checkpoint heights. Under `commitment-budget`, it also checks stored tree sizes across gaps. A stride that meets the selection skips replay and checkpoint-content comparison. For a stride that needs more checkpoints, the pass replays from its first stored checkpoint and writes missing rows only if the replay reproduces every existing checkpoint byte for byte, including the ending cadence checkpoint. Replay remains the answer for a height the pass has not reached on a sparse store and, under `commitment-budget`, for heights between budgeted checkpoints.

[Wallet data plane](../architecture/wallet-data-plane.md) describes what each method returns. [Capabilities](../reference/capabilities.md) lists the capability strings.

## Consequences

- Compatibility work has one general target instead of per-app exceptions.
- Operators have one serving posture: build a complete store, then run readers against it.
- Missing history becomes a deployment or readiness failure, not a hidden query fallback.
- A running reader keeps serving tree state, blocks, and transparent reads while the node is down ([ADR-0016](0016-wallet-serving-readiness.md)).
- Serving stores are larger and slower to build than near-tip stores. Local tests use disposable stores instead of a near-tip construction.
- A tree-state read at a height with a stored checkpoint is a stored read. It returns the stored frontier bytes without hashing and takes no replay slot. Its integrity rests on the checks made when the row was written and on RocksDB block checksums, so a row written with frontier bytes that do not derive its root, or with one pool's frontier in another pool's place, would be served as stored; the write-side checks exist to prevent that.
- The background verification bounds how long a damaged row is served to about one verification cycle, at a fixed CPU cost instead of one that grows with traffic; [Chain ingestion](../architecture/chain-ingestion.md#tree-state-verification) gives the cycle time. It checks each row on its own, so it cannot detect a row that holds another height's valid trees, or an Orchard frontier with its own root in the Ironwood position or the reverse, because those pools hash alike; live following's comparison with the node and densification's stride replay cover those cases when the row is written. Under the commitment-budget selection at its default budget of 1,024, a read between checkpoints replays fewer than 1,024 commitments, an estimated 65 to 130 ms instead of the several seconds a 99-block replay costs in the dense 2022 range, but it still takes a replay slot. A read the pass has not reached replays at most 99 stored blocks.
- Storing every settled block's tree state, the default, adds about 2.4 GB uncompressed for Mainnet history. The 1,024-commitment budget adds about 0.13 GB. Both are estimated from the row encoding at Mainnet tree sizes and not yet measured on a full Mainnet build, and neither includes compression. Live following already adds one row per block.
- Writing every block's checkpoint during fresh construction cross-checks each frontier while the commitment trees are already being advanced, avoiding a second replay of every commitment in constructed history afterward. That moves per-block root derivation and checkpoint SST staging ahead of READY publication on the serial loader, increasing time-to-READY while reducing combined construction-plus-densification CPU; full Mainnet construction impact awaits qualification. For existing sparse stores, the background pass costs one replay of every commitment in constructed history plus two root derivations per pool for each row it writes (an estimated 4 to 5 CPU-hours on Mainnet for `every-block`; under `commitment-budget` the root derivations nearly vanish and the replay dominates). A cap on blocks replayed per second bounds the background pass's reads and writes on average, and its writes are small synced batches between live commits. A recorded watermark lets a restart resume without rescanning densified history.
- The stored rows are as trustworthy as the stored checkpoints they reproduce. Construction derives and cross-checks its checkpoints from the blocks it loads and checks only its build-tip tree state against the node. Live following checks every checkpoint it stores against the node's tree state for that block. On a sparse store, a stride below the build tip is anchored only on construction's cadence checkpoints; the stride that holds a build tip off the cadence must also reproduce construction's node-checked build-tip checkpoint and the node-checked rows live following stored above it, including the checkpoint that ends the stride. For a stride that needs more checkpoints, the replay establishes that the stored blocks reproduce every checkpoint from the seed through the end of that stride. It does not compare the rows it adds with the node, so a stride whose stored blocks and existing checkpoints were all altered consistently would pass, as it would for the read-side replay today.
- A canonical rebuild under the default `every-block` setting writes checkpoints for every block during construction; a rebuild with densification disabled or `commitment-budget` selected writes the 100-block cadence and build tip until the background pass runs.
- Adding an optional field touches the proto, the capability registry and its tests, and the handler that fills it, in one change.
- Consumers branch on field presence and on `ServerInfo` capabilities, never on sentinel values.

## Alternatives rejected

- **Fall back to the node for missing artifacts.** It blurs the source of truth, makes readiness lie, and turns query runtimes into partial node proxies. Repair tools may use the node to rebuild artifacts. Public reads may not.
- **A per-wallet coverage profile.** It recreates the app-specific design this decision avoids.
- **Bounded-history serving stores.** Narrowing coverage needs proven demand. The first stable profile favors correct wallet behavior.
- **Answer `GetTreeState` by proxying the node, as lightwalletd does.** Tree-state reads would then fail during node outages.
- **Keep replaying between 100-block checkpoints.** Wallet engines that fetch blocks in byte-sized pieces ask for a tree state at nearly every piece boundary, so on a constructed store almost every such request replays, and replay runs one request per CPU. The replay slots, not the block streams, then bound how many wallets can restore at once.
- **Store tree nodes once and assemble any tree state from them.** It stores less than a row per block, but it needs a storage-layout break, a rebuild, new reorg handling that truncates nodes above a fork, and a different per-request check. A later storage break may revisit it if measured sizes call for it.
- **Store checkpoints only at the heights wallet SDKs ship as birthdays.** It helps only the first request of a restore.
- **Re-derive each pool's root on every stored tree-state read.** It costs about 4 ms of CPU for a three-pool checkpoint to re-check a row that was validated when it was written, and a cache of recent roots does not help because wallets ask for distinct heights. RocksDB block checksums already detect corruption at rest, and the background verification re-checks every row at a fixed, bounded cost instead of a cost that grows with traffic.
- **Exit ingest when the background verification finds a damaged row.** The writer does not read the damaged history and can still commit. An exit would leave an orchestrator restarting a process that finds the same row on each start, while parking readiness keeps ingest up to report the damage to its readers.
- **Refuse `CanonicalControl.WriterStatus` while the store is damaged.** Readers would see only an unreachable writer: they would keep serving until their staleness ceiling passed and then report `writer_status_unavailable`, the projector would fail its convergence, and a supervisor could not tell damage from an outage. A typed field in the status lets readers refuse at once with a cause that names the damage, and lets the projector and supervisors treat it as a park.
- **Sentinel values for absent fields.** A consumer cannot tell "unresolved" from a real zero fee or balance.
