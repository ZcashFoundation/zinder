## [0.17.0] - 2026-11-17

### Changed

- Wallet-serving `zinder-query` and `zinder-compat-lightwalletd` now read every serving generation through one canonical and one wallet block cache, so `storage.canonical.rocksdb.block_cache_bytes` and `wallet.rocksdb.block_cache_bytes` cap the whole process instead of each of up to four generations, and compact-blocks `zinder-compat-lightwalletd` reads both of its generations through one canonical cache. No setting or default changes, and the block-cache ceiling falls by up to three quarters in wallet serving and by half in compact-blocks serving. An existing override now sets the process total, so keep it or lower the container memory limit to reclaim the difference; in the wallet-serving container, the wallet setting also still sizes the projector's writer cache. Each store's `default` column family now reads through the configured cache instead of a separate 32 MiB cache in every RocksDB instance. Wallet serving exports the block-cache gauges as `store_role="canonical_secondary"` and `store_role="wallet_secondary"` plus `zinder_wallet_serving_pair_publisher_open_generations`, compact-blocks serving exports them as `store_role="canonical_secondary"`, and both export memtable memory and the new `zinder_store_table_reader_memory_bytes` summed over open generations, sampled at most every 15 seconds. ([#254](https://github.com/ZcashFoundation/zinder/pull/254))

### Fixed

- Wallet subtree-root reads, lightwalletd `GetSubtreeRoots` and the native `SubtreeRoots` RPC, now serve the root computed from the block that completed each subtree. Previously, a node that switched to a competing block at that height while ingest read the roots could leave the competing block's root stored without an error. If the node keeps reporting a different root for a block it still holds, ingest stops with "source ... subtree N root differs from the root derived from block ..."; check that the node is synced and healthy, then restart ingest, which resumes from the last committed block. Roots stored before this release are not rechecked, so rebuild the store if a reorg may have crossed a subtree boundary while it was written. ([#252](https://github.com/ZcashFoundation/zinder/pull/252))
- lightwalletd `GetBlockRange` and `GetBlockRangeNullifiers` now read at most 2 MiB of compact blocks per chunk as well as at most 1,000 blocks, so one chunk no longer holds up to 1,000 large blocks at once. A range of large blocks is read in several chunks even when it spans fewer than 1,000 heights, so near the tip it can end early with `ABORTED` or `OUT_OF_RANGE`, as wider ranges already could. The new `compat.max_concurrent_block_range_streams` setting (`ZINDER_COMPAT__MAX_CONCURRENT_BLOCK_RANGE_STREAMS`, default 100) refuses further block-range streams with `RESOURCE_EXHAUSTED`. `zinder_compat_block_range_streams_open` and `zinder_compat_block_range_stream_refusals_total` show how close the server runs to it. Size `ZINDER_COMPAT_MEMORY_LIMIT` for the limit as the lightwalletd compatibility reference describes. The compatibility server also limits each HTTP/2 connection to 200 concurrent streams and closes connections that stop answering keepalive pings. ([#253](https://github.com/ZcashFoundation/zinder/pull/253))
