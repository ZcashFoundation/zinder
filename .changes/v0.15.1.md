## [0.15.1] - 2026-11-16

### Changed

- Following a block no longer derives the same note-commitment-tree roots repeatedly, so `zinder-ingest` uses far less CPU per block while catching up after downtime or replaying a deep reorg. On a 20,122-block Testnet replay, canonical preparation of a block with no transparent activity fell from about 9 ms to under 2.5 ms. ([#213](https://github.com/ZcashFoundation/zinder/pull/213))
- A wallet store that follows the canonical chain no longer re-reads its whole reorg-undo window on every block. After one full check when it opens, each append reads only the undo rows it changes, which lowers `zinder-projector` read load per block, most noticeably on read-limited storage. The full check still runs after a failed write, on every reorg, and on every reconciliation. ([#212](https://github.com/ZcashFoundation/zinder/pull/212))
- The wallet projection digest and the UTXO-set commitment now cost about 64% less CPU per transparent output row, which shortens wallet work on blocks with many transparent outputs and lowers the CPU cost of wallet builds. Digest values and stored bytes are unchanged, so existing wallet stores and bundles stay valid. ([#214](https://github.com/ZcashFoundation/zinder/pull/214))
- The four hash-keyed wallet column families now carry lookup filters, so `zinder-projector` answers its checks that an output is not already recorded without reading a data block. Existing wallet stores keep working and gain filters as RocksDB rewrites their files; rebuild the wallet projection side by side to get the full effect at once. Filter blocks share the wallet block cache at about 0.9 bytes per row, so size `block_cache_bytes` for them as ADR-0020 describes. Rolling back to an earlier release is safe. ([#215](https://github.com/ZcashFoundation/zinder/pull/215))
- Within one wallet transition, `zinder-projector` now reads each wallet row from RocksDB once instead of several times: at most four point reads for each spent or created transparent output, down from about seven and eight, while the transition stays within `projector.follow.max_transition_logical_bytes`. ([#216](https://github.com/ZcashFoundation/zinder/pull/216))

### Fixed

- A wallet transition now publishes one write batch with the final value of each row it touches, so reorg and reconciliation transitions plan fewer bytes against `projector.follow.max_transition_logical_bytes`, which now counts each distinct touched row twice plus the control record. A transition that still exceeds the limit stops `zinder-projector` with an error that names the setting, `ZINDER_PROJECTOR__FOLLOW__MAX_TRANSITION_LOGICAL_BYTES`, and the recovery; the wallet-serving and VM runbooks describe the steps. ([#217](https://github.com/ZcashFoundation/zinder/pull/217))
