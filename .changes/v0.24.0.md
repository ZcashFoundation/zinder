## [0.24.0] - 2026-11-23

### Added

- Operators can compare two wallet reader binaries on the same private fixture, verify block-range response bytes against an independent oracle, and evaluate paired results against their own performance tolerances. ([#469](https://github.com/ZcashFoundation/zinder/pull/469))
- Set `deployment.profile = "light-wallet"` in the standard ingest and compatibility binaries to serve wallets with complete compact history and without raw blobs or a wallet projection. Configure one node with transparent address indexes. Existing schema 7 stores can serve readers whose minimum requirements they meet. A canonical layout change requires a fresh store. A seven-day build-beside rollback period is optional. Keep the previous binaries and their matching store if you need a fallback. ([#507](https://github.com/ZcashFoundation/zinder/pull/507))
- The wallet range probe reports pauses between successive blocks so operators can compare the longest pause across verified requests and inspect the individual frame arrivals. ([#519](https://github.com/ZcashFoundation/zinder/pull/519))
- `zinder-projector` exports `zinder_wallet_projection_build_stage_duration_seconds`, a histogram labeled by `stage` with the wall time of each non-overlapping stage of a fresh wallet build, recorded when the build publishes READY. The stages are listed in the metrics reference. ([#524](https://github.com/ZcashFoundation/zinder/pull/524))
- `projector.build.accumulator_hashing_workers` (`ZINDER_PROJECTOR__BUILD__ACCUMULATOR_HASHING_WORKERS`) sets how many threads a fresh wallet build uses to hash rows into its projection digest and UTXO set commitment, and how many key ranges cold validation reads the unspent and spent output families in. It defaults to the logical CPUs the projector may use, at most 4, and accepts 1 to 64; the projector refuses a larger value at startup. A build therefore uses more CPU by default: a full Testnet wallet build finished about 48% sooner on 4 cores and 29% sooner on 2, with about 5% more total CPU time and the same memory and temporary disk. Set it to 1 to hash on the build thread as before. The published wallet is the same at any value. `zinder-core` adds `TransparentUtxoSetCommitment::combine`. ([#525](https://github.com/ZcashFoundation/zinder/pull/525))

### Changed

- The lightwalletd listener sends signed-history `GetBlockRange` blocks of 32 KiB or more from the stored segment without copying them into the gRPC encode buffer. Responses are unchanged. In `zinder-proto`, `EncodedBlockRangeStream` now yields `EncodedBlock`, a gRPC length-prefixed `CompactBlock` message, so custom `EncodedBlockRange` implementations must wrap their payloads with `EncodedBlock::encode` or `EncodedBlock::from_length_prefixed`. ([#495](https://github.com/ZcashFoundation/zinder/pull/495))
- The lightwalletd listener now hands `GetBlockRange` response data to HTTP/2 without copying it in the send-stall bound when every chunk keeps at most 512 KiB, and at most twice its own bytes, alive, which holds for every stored Mainnet block so far. A client that stops reading a range stream can therefore keep up to about 2 MiB of stored blocks in memory per stalled stream, instead of up to about 592 KiB of copied buffers. Other methods are unchanged. `zinder-proto` adds `BoundedChunkRetention` and `EncodedBlock::from_length_prefixed_in`; a large message built with `EncodedBlock::from_length_prefixed` is now copied in 64 KiB pieces. ([#501](https://github.com/ZcashFoundation/zinder/pull/501))
- Readers no longer adopt a canonical store replaced at the same path while running when its workload, raw-blob retention, first retained block height, subtree-root coverage mode, or first retained subtree-root index of any shielded pool differs. Earlier releases adopted a replacement with a different first retained block height or subtree-root coverage without a restart. Compact-blocks and light-wallet compatibility now report `schema_mismatch`, and native query and wallet-mode compatibility report `storage_unavailable`, until you restart the reader, which then admits the new store if it meets the reader's requirements. ([#507](https://github.com/ZcashFoundation/zinder/pull/507))
- A `GetBlockRange` response now sends its first frame once it holds 8 KiB of blocks, so behind a gateway that forwards whole HTTP/2 frames a wallet receives the first block in the first round trip of a connection that has been idle, unless the blocks in that frame are large enough to need more than one round trip on their own. Response bytes and later frames are unchanged. ([#521](https://github.com/ZcashFoundation/zinder/pull/521))
- Looking up a mined transaction by ID, as `GetTransaction` does, now reads the transaction's location from canonical storage once instead of twice. Responses are unchanged. ([#523](https://github.com/ZcashFoundation/zinder/pull/523))
- A fresh wallet build's sorters that end with at most 64 runs now merge them while the build reads them, instead of writing a merged run to disk first. A full Testnet wallet build finished about 11% sooner and needed half the peak temporary files for its address sorts. The temporary-file limits refuse a build at the same settings as before, and the published wallet is unchanged. ([#524](https://github.com/ZcashFoundation/zinder/pull/524))
- First sync and live ingest now parse each block once. Transaction identifiers come from the block parse instead of a second parse of every version 5 and 6 transaction, and transaction byte ranges are recorded during the parse instead of serializing each transaction again. On a dense Mainnet range at four cores, time to READY fell by about 40% in local tests. Stored data is unchanged, and no operator action is needed. ([#529](https://github.com/ZcashFoundation/zinder/pull/529))

### Fixed

- Wallet and compact-blocks listeners with a signed settled-history catalog no longer queue `GetBlockRange` requests that select transparent data, or any pool set other than the default shielded projection, behind signed-read permits. These requests read canonical storage immediately with the normal chunk budget. ([#506](https://github.com/ZcashFoundation/zinder/pull/506))
- Listeners whose signed settled-history catalog starts above height 1 no longer queue default shielded `GetBlockRange` requests for heights below the catalog behind signed-read permits. Those requests read canonical storage immediately with the normal chunk budget. ([#509](https://github.com/ZcashFoundation/zinder/pull/509))
- A descending `GetBlockRange` that overlaps the signed settled-history catalog but cannot read signed segments, such as one that runs from inside the catalog to below it, no longer waits for a signed-read permit. It reads canonical storage immediately with the normal chunk budget. ([#511](https://github.com/ZcashFoundation/zinder/pull/511))
- Docker builds that reuse a Cargo target cache now recompile every Zinder workspace crate from the tree being built. Before, a build of a source tree whose files carried older modification times, such as one extracted from `git archive` or a tarball, could reuse another tree's compiled Zinder crates and produce a binary that reported the new commit but ran some old code. The `zinder-ingest-live-tests` image now builds with Rust 1.100 again. ([#513](https://github.com/ZcashFoundation/zinder/pull/513))

### Security

- Public gRPC listeners in zinder-query, zinder-compat-lightwalletd, and zinder-explorer now close a connection after the server has reset 1,024 of its streams because of the client's protocol errors. Previously there was no limit. ([#517](https://github.com/ZcashFoundation/zinder/pull/517))
