## [0.11.0] - 2026-11-14

### Added

- Zinder now certifies Zakura 1.8.6 as a node runtime alongside Zebra 7.0.0. The live and lightwalletd parity suites run against both nodes on the same Regtest schedule through NU7, nightly and on pull requests that touch node-facing code, and a release requires both nodes to pass. `deploy/zakura/regtest.toml` starts a Zakura Regtest node on that schedule. `deploy/zebra/regtest.toml` now includes the same zero-value NU6.1 lockbox disbursement that Zakura requires, so both nodes use the same funding configuration. ([#149](https://github.com/ZcashFoundation/zinder/pull/149))
- `zinder-ingest` can now reach a node's indexer gRPC endpoint over TLS, including mutual TLS, which a Zakura indexer on any non-loopback address requires. An `https://` `node.indexer_grpc_addr` negotiates TLS. The new `[node.indexer_tls]` section (`ca_cert_path`, `client_cert_path`, `client_key_path`, and `server_name`, or the matching `ZINDER_NODE__INDEXER_TLS__*` variables) names a CA bundle, a client certificate and key, and a server name override, all as file paths. Ingest checks those files at startup and exits with a configuration error when one is missing or holds no certificate or key. On platforms that deliver secrets only as environment variables, the `zinder-canonical-runtime` and `zinder-wallet-serving` images accept `ZINDER_NODE__INDEXER_TLS__CA_CERT_PEM`, `ZINDER_NODE__INDEXER_TLS__CLIENT_CERT_PEM`, and `ZINDER_NODE__INDEXER_TLS__CLIENT_KEY_PEM`, and write them to files that only the `zinder` user can read. Every Zinder binary refuses these PEM variables when they are set directly. ([#150](https://github.com/ZcashFoundation/zinder/pull/150))
- Compose deployments can now stream mempool events from a node whose indexer gRPC listener requires mutual TLS, such as a Zakura node in another container. Merge `deploy/docker-compose.indexer-tls.yml`, set `ZINDER_NODE__INDEXER_GRPC_ADDR` to the node's `https://` indexer URL, and set `ZINDER_INDEXER_TLS_DIR` to a directory that holds `ca.pem`, `client.pem`, and `client-key.pem`. ([#151](https://github.com/ZcashFoundation/zinder/pull/151))

### Changed

- The single-host Compose deployment no longer defaults to a Zebra node in Z3. Compose refuses to start unless the env file sets `ZINDER_DEPLOY_NETWORK` (replacing `Z3_NETWORK_LOWER`), `ZINDER_SOURCE_NETWORK_NAME`, `ZINDER_SOURCE_COOKIE_VOLUME_NAME`, `ZINDER_NETWORK__NAME`, and `ZINDER_NODE__JSON_RPC_ADDR`. The checked-in env files now poll the mempool over JSON-RPC instead of streaming from `http://zebra:8155`. New `deploy/.env.zakura-mainnet` and `deploy/.env.zakura-testnet` files attach a Zakura node, and `deploy/node-cookie-permissions.yml` makes a non-Z3 node's cookie readable to Zinder. Update `/etc/zinder/env` as the VM deployment runbook describes before upgrading. ([#144](https://github.com/ZcashFoundation/zinder/pull/144))
- `zinder-ingest` now refuses to start against a pruned node. At startup it reads `pruned` from `getblockchaininfo` and requires the new `historical_block_bodies` capability. A node that reports `pruned: true` or omits the field makes readiness report `node_capability_missing`, and the process exits before it touches the store. This applies to restarts of an existing store too, so point ingest at an archive Zebra or Zakura node. `zinder-query` and `zinder-compat-lightwalletd` still accept pruned nodes. A Zakura node built by verified-commitment-trees fast sync permanently refuses tree states and subtree roots below its last checkpoint, and those refusals are now classed `capability_missing`. Native query returns them as the non-retryable `NODE_CAPABILITY_MISSING` instead of a retryable node error. ([#145](https://github.com/ZcashFoundation/zinder/pull/145))
- `zinder-ingest` now refuses to start when `ingest.construction.source_segment_max_blocks` (`ZINDER_INGEST__CONSTRUCTION__SOURCE_SEGMENT_MAX_BLOCKS`) is above 1000. Each block in a source segment is one JSON-RPC batch entry, and Zakura refuses batches with more than 1,000 entries. The default of 64 is unaffected. If you set a larger value, lower it to 1000 or less before upgrading. ([#146](https://github.com/ZcashFoundation/zinder/pull/146))
- The `zinder-wallet-serving` image now passes each process exactly the `ZINDER_*` variables its binary accepts, so any documented `zinder-ingest`, `zinder-projector`, or `zinder-query` variable, such as `ZINDER_PROJECTOR__BUILD__MAX_TEMPORARY_FILE_BYTES_PER_SORTER`, can be set on the container and reaches only the processes that read it. Variables no process reads are logged by name at startup. The construction deadlines are now set by `ZINDER_WALLET_SERVING__CANONICAL_CONSTRUCTION_DEADLINE_SECONDS` (default `10800`) and `ZINDER_WALLET_SERVING__WALLET_CONSTRUCTION_DEADLINE_SECONDS` (default `7200`), and any other `ZINDER_WALLET_SERVING__*` name stops the container at startup; a Mainnet build from an empty volume needs the longer values in the wallet-serving runbook. The image now refuses to start without `ZINDER_NODE__INDEXER_GRPC_ADDR`, because JSON-RPC mempool polling re-reads the whole mempool after every block and drops ingest readiness when that takes longer than 30 seconds; set it to the node's indexer gRPC URL before upgrading. The supervisor no longer restarts the container over occasional brief readiness drains: an answered unready stretch counts as a flap episode only after 60 seconds, while shorter drains still count toward the 900-second unready budget. ([#166](https://github.com/ZcashFoundation/zinder/pull/166))

### Fixed

- Reads pinned to a chain epoch with `at_epoch_id` no longer fail as soon as a new block arrives. `zinder-query` keeps serving the two most recently replaced epochs, each for up to one minute after it is replaced, so a wallet that reads the unspent outputs of its transparent receivers one by one under a single pin finishes across a new block instead of restarting. A `TransparentAddressTxIdsInRange` continuation resumes on the epoch that issued it during the same window. The first page of that history read carries no epoch pin and still answers only from the current epoch. On a transparent-serving `zinder-compat-lightwalletd`, `GetTaddressTxids` and `GetTaddressTransactions` read history and transactions at one epoch, so a new block during the request no longer fails it. Each retained epoch keeps its own canonical and wallet secondaries open, so the query process can hold up to four serving pairs at once, about 1.4 GiB on the `zinder-wallet-serving` image. ([#171](https://github.com/ZcashFoundation/zinder/pull/171))
- The default wallet-build spill ceiling no longer stops a Mainnet wallet build from genesis. A complete Mainnet build with the shipped wallet-serving image still needs longer construction deadlines (#158). `projector.build.max_temporary_file_bytes_per_sorter` (`ZINDER_PROJECTOR__BUILD__MAX_TEMPORARY_FILE_BYTES_PER_SORTER`) now defaults to 206158430208 (192 GiB) instead of 64 GiB, because the largest sorter of a Mainnet build needs about 99 GB. Several sorters spill at once, so keep about 130 GB free on the volume when a Mainnet wallet construction starts. When the setting is too small, `zinder-projector` now usually stops during the canonical scan instead of after it, with an error that names the setting and its environment variable. A refusal before a sorter has seen all of its records gives only a lower bound, so unset the setting or raise it well above that figure. Explicitly configured values are unchanged. ([#164](https://github.com/ZcashFoundation/zinder/pull/164))
- A `zinder-projector` that crashes or is killed during wallet construction now resumes as soon as it restarts with the same `projector.build_owner_hex`. Previously its leftover construction leases refused the restart for up to `projector.lease_duration_seconds`. A projector with a different owner value is still refused until the lease expires, and the error now names the owner that holds the build; the initial-sync runbook describes how to recover. A second projector running against the same wallet path is refused while the first builds, even with the same owner value, and a crash before the wallet store is created no longer blocks the next build. ([#167](https://github.com/ZcashFoundation/zinder/pull/167))
- `zinder-ingest` now stops within the wallet-serving supervisor's 20-second grace window when it is terminated while fresh canonical construction streams blocks. SST finalization and publication cannot be interrupted, so ingest finishes them before it exits. Construction stops without admitting a store, and the next start rebuilds it, or installs a staged READY store when publication had already finished. During construction, ingest no longer logs `mempool_durable_replay_failed` or `mempool_event_retention_failed` with `DeadlineExceeded`, because the mempool owner and mempool-event retention now start only after the writer admits a READY store. ([#168](https://github.com/ZcashFoundation/zinder/pull/168))
- Explorer views now publish the transparent-address ranking, so `ExplorerQuery.ServerInfo` advertises `explorer.transparent_address.activity_v2` and `explorer.transparent_address.ranking_v1`, and `TransparentAddressActivity` returns address summaries. A fresh Explorer views build includes the ranking from genesis. A store built by Zinder 0.10.0 needs no rebuild: after the upgrade, `zinder-ingest` builds the ranking from canonical history while the other views keep following the tip, logs `transparent_address_ranking_activated` when it serves, and resumes the build after a restart. ([#170](https://github.com/ZcashFoundation/zinder/pull/170))
- A new block no longer makes wallet serving briefly not ready. `zinder-ingest` keeps answering live mempool reads at the previous tip while it rebuilds the mempool view for the new one, so `MempoolSnapshot` no longer fails with "live mempool index is hydrating" after each block, and neither ingest (`syncing`) nor `zinder-query` (`ingest_control_unavailable`) withdraws readiness. A mempool read at the new tip waits up to five seconds for the rebuilt view. Ingest still reports `syncing` when its mempool view trails the canonical tip for 30 seconds. `zinder-query` and `zinder-compat-lightwalletd` also keep publishing new serving pairs while a long request, such as a transparent unspent-output read for an address with millions of outputs, holds an older one, so the reader no longer stalls at `replica_lagging` until a restart. ([#172](https://github.com/ZcashFoundation/zinder/pull/172))
