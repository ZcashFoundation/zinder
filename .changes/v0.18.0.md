## [0.18.0] - 2026-11-18

### Added

- `zinder-ingest` can now fail over between node endpoints. Configure fallback endpoints as `[node_fallbacks.1]`, `[node_fallbacks.2]`, and so on, or as `ZINDER_NODE_FALLBACKS__1__JSON_RPC_ADDR` and the other `[node]` fields under a position. `[node]` stays position 0, and a single-endpoint deployment behaves and prints its configuration as before, except that `--print-config` and the `canonical_writer_started`, `upstream_health_probe_started`, and `upstream_health_endpoint_unreachable` log events now show every node URL with its user information, query, and fragment replaced by `[REDACTED]`, and a `[node.health]` `/ready` probe that gets no answer within two seconds, or within the poll interval when that is shorter, falls back to `getblockchaininfo` in the same poll instead of waiting out the poll interval. With fallbacks configured, ingest checks every endpoint at startup, including its genesis block, and starts on the first one that passes, without waiting for higher positions once a lower one passes. An endpoint is excluded until restart only when it reports pruned storage, lacks a required capability, answers for another network, or advertises another network-upgrade table. An endpoint that times out, or that was still being checked when ingest started, is checked again while ingest runs. While following the chain, ingest switches between blocks after three consecutive recoveries of one transport class, `node_unreachable` or `stream_disconnected`, or after the active node has reported not ready for five minutes. It prefers an endpoint that holds its visible tip. It switches to an endpoint on another branch only when that branch shares the settled tip, so the switch replaces blocks within the reorg window, and never to an endpoint whose chain differs at or below the settled tip. Ingest does not switch back on its own; a restart starts at `[node]` again. `/readyz` and the ops `ReadinessReport` report `active_node.position` when fallbacks are configured. New metrics: `zinder_ingest_node_endpoint_active{position}`, `zinder_ingest_node_endpoint_state{position,state}`, and `zinder_ingest_node_endpoint_switches_total{from_position,to_position,failure_class}`. New log events: `node_endpoint_admitted`, `node_endpoint_unreachable`, `node_endpoint_excluded`, `node_endpoint_deferred`, `node_endpoint_state_changed`, `node_endpoint_skipped`, `node_endpoint_switched`, and `node_endpoint_switch_unavailable`. `zinder-query`, wallet-mode `zinder-compat-lightwalletd`, and `zinder-explorer` accept and validate the same list, and refuse a fallback list without `[node]`. `zinder-projector` and compact-blocks compatibility read no node and reject the list as they reject `[node]`. The single-volume images route `ZINDER_NODE_FALLBACKS__*` to ingest, query, and the Explorer, never to the projector, accept `ZINDER_NODE_FALLBACKS__<N>__INDEXER_TLS__*_PEM`, and require each fallback's `INDEXER_GRPC_ADDR` in the wallet-serving image. A new Compose overlay, `deploy/docker-compose.node-fallback.yml`, attaches a second node. Every endpoint must advertise exactly the network-upgrade table the store admitted. Construction admits source responses against the largest `max_response_bytes` in the list, so startup refuses a `source_fetch_max_in_flight_bytes` override below it. When upgrading nodes, upgrade the one ingest is not reading from, then the other, then restart ingest. ([#259](https://github.com/ZcashFoundation/zinder/pull/259))
- `zinder-query` and wallet-mode `zinder-compat-lightwalletd` now broadcast transactions through the ordered node list: `[node]` first, then each `[node_fallbacks.N]` endpoint. Each endpoint is verified on first contact before any transaction reaches it, as `[node]` already was. A broadcast moves to the next verified endpoint when one is unreachable, including when its `broadcast_timeout_secs` expires, or rejects the transaction for its consensus branch. Any other answer is returned. After such a move, the endpoint that answered is tried first from then on, with no timed failback; skipping an endpoint that is not verified yet moves nothing. The node probe also moves past a verified endpoint that stops answering, so an idle reader stays ready and its next broadcast pays no timeout. When every verified endpoint is unreachable, the broadcast fails with `NODE_UNAVAILABLE` and readiness is unchanged. With fallbacks, set `broadcast_timeout_secs` on every endpoint well below wallet request deadlines: a fallback does not inherit the value of `[node]` and otherwise waits for its own `request_timeout_secs`. The node-fallback Compose overlay sets 7 seconds for fallback 1. Readers verify every endpoint on the `[node]` health poll interval and ignore a fallback's. Each endpoint is verified on its own schedule, so one that hangs until its request timeout delays neither another endpoint's verification nor the node probe's move past a verified endpoint that stopped answering. An endpoint that timed out may have accepted the transaction. When an earlier endpoint in the same broadcast was unreachable, a later duplicate or queued answer is reported as accepted with the transaction id computed from the submitted bytes, so lightwalletd wallets receive `errorCode` 0 instead of -27 or -25. For the same reason, a broadcast that no endpoint answered fails with the retryable `NODE_UNAVAILABLE` whenever an endpoint was unreachable, even if another endpoint rejected it for its consensus branch. Verification checks a node's activation table through the height after the served tip, the block a broadcast targets, and is repeated as soon as the writer admits a new network-upgrade schedule revision or that height crosses an activation in the writer's schedule or in the node's own table. Every broadcast also checks the node's verified table against the writer's current schedule through that height, so a node that schedules NU7 at 700 while the writer schedules it at 703, or that still schedules NU7 at 700 after the writer moves it to 703, receives no transaction once a broadcast targets height 700. Until the repeat passes, an endpoint whose verified table still agrees keeps its earlier verification for up to one minute from when the reader first sees the new schedule or height, both while the repeat waits on the node and after it is inconclusive, for example because the node has not received the latest block yet, and the reader retries every two seconds. An endpoint that lacks `sendrawtransaction` or advertises a disagreeing activation table is excluded and verified again after a backoff of 30 seconds that doubles up to 5 minutes, instead of at every poll interval. `ServerInfo.node` reports the first verified endpoint in broadcast preference order. New metrics: `zinder_wallet_broadcast_endpoint_attempts_total{position,outcome}`, `zinder_wallet_broadcast_endpoint_state{position,state}`, and `zinder_wallet_broadcast_endpoint_switches_total{from_position,to_position,cause}`. New log events: `wallet_node_excluded`, `broadcast_endpoint_switched`, and `broadcast_reported_accepted_after_unreachable_endpoint`, and `wallet_node_reverification_inconclusive`; `wallet_node_verified` and `wallet_node_verification_failed` now carry the endpoint `position`. `zinder-explorer` still reads only `[node]`. ([#260](https://github.com/ZcashFoundation/zinder/pull/260))
- `zinder-compat-lightwalletd` can now answer the lightwalletd `Ping` load-testing RPC. Set `compat.ping_very_insecure = true`, `ZINDER_COMPAT__PING_VERY_INSECURE=true`, or pass `--ping-very-insecure`, as on lightwalletd. Both serving modes then report the number of `Ping` calls in flight and sleep for the requested interval, as `lightwalletd --ping-very-insecure` does. Each call holds a server task for as long as the client asks, so enable it only while load testing. The setting is off by default, and `Ping` is then refused with `FAILED_PRECONDITION`. ([#284](https://github.com/ZcashFoundation/zinder/pull/284))

### Changed

- `TreeStateAtHeight` and the lightwalletd-compatible `GetTreeState` now serve the tree state at every indexed height from Zinder's own store, and no longer call `z_gettreestate` on the node. A height between stored checkpoints is rebuilt from the nearest checkpoint and the stored compact blocks, and returns the same `finalState` bytes as before. Existing stores need no rebuild, and `wallet.read.tree_state_at_height_v2` is now always advertised. Each wallet-serving process rebuilds at most one tree state per CPU at once. A request that needs a rebuild while every slot is busy fails at once with `RESOURCE_EXHAUSTED` and the new `TREE_STATE_REPLAY_LIMIT_REACHED` reason; clients should retry with backoff. Heights with a stored checkpoint, which include every block followed live, are never refused this way. Two new metrics track the work: `zinder_query_tree_state_replayed_blocks` samples the blocks each rebuild replays, and `zinder_query_tree_state_replay_refusals_total` counts refusals. `zinder-client` reports the refusal as `ErrorReason::TreeStateReplayLimitReached` with `RetryPolicy::RetryWithBackoff`. Dashboards that attributed tree-state latency to node calls should read these instead. Damaged history between checkpoints, such as a missing compact block or a broken parent link, now fails tree-state requests with `STORAGE_UNAVAILABLE` instead of being masked by the node's answer. ([#256](https://github.com/ZcashFoundation/zinder/pull/256))
- `zinder-query` and `zinder-compat-lightwalletd` now stay ready while their Zebra node is unavailable or still syncing, and native query also stays ready while ingest control is unavailable, until `storage.serving_pair_staleness_ceiling_ms` passes. Stored reads, compact-block sync, `GetLightdInfo`, and the trusted-TLS compatibility route keep answering. Only the requests that need the dependency fail: broadcast returns `UNAVAILABLE` with `NODE_UNAVAILABLE`, and native query's mempool methods and unmined `Transaction` lookups return `UNAVAILABLE` with `UPSTREAM_UNREACHABLE` while ingest control is down. When ingest is reachable but its canonical writer has stopped or misses its 60-second reply timeout, `IngestControl` requests return `UNAVAILABLE` with `STORAGE_UNAVAILABLE` instead of `DEADLINE_EXCEEDED` or an `UNAVAILABLE` without a reason. Native query forwards that refusal from a stopped writer, but it ends its own ingest-control calls after 15 seconds, so a stalled writer reaches its callers as `UPSTREAM_UNREACHABLE`. While the writer's live mempool hydrates or rebuilds from its node, `MempoolSnapshot` returns `UNAVAILABLE` with `NODE_UNAVAILABLE`, and a `MempoolEvents` subscription replays its retained events and then ends with the same status instead of staying open and silent. Resubscribe from the last delivered cursor with backoff. That ending raises the native contract revision to 9, so a consumer that relies on it requires revision 9, and `zinder-query` and wallet-mode compatibility admit only a revision 9 `zinder-ingest`: upgrade ingest and the readers together. An open lightwalletd-compatible `GetMempoolStream` also ends with `UNAVAILABLE` in that case. Compact-blocks compatibility ends each writer-status read after 15 seconds, so a writer that never answers still drains it once `storage.serving_pair_staleness_ceiling_ms` passes. A canonical writer parked by `reorg_window_exceeded` still refuses every request. `/readyz` lists each unhealthy dependency in a new `degraded` array of `{"input", "dependency_cause"}` entries after the top-level `cause`, and wallet-serving readers add `served_epoch_age_seconds`, the time since the writer committed the chain view they serve; the `zinder.v1.ops.ReadinessReport` message gains the matching `degraded` and `served_epoch_age_seconds` fields. The wire change is additive, but Rust code that builds `zinder_proto::v1::ops::ReadinessReport` with an exhaustive struct literal must add the two fields or end the literal with `..Default::default()`. Native query no longer reports `node_unavailable`, `upstream_not_ready`, `node_capability_missing`, or `ingest_control_unavailable` as its own cause, and a writer that reports `upstream_not_ready` now appears as that cause under `degraded` instead of `ingest_control_unavailable`. Alert on the new `zinder_readiness_dependency_state{input, cause}` and `zinder_readiness_served_epoch_age_seconds` metrics instead of reader 503s; the bundled Prometheus rules add `ZinderDependencyDegraded` and `ZinderServedChainStale`, and the bundled Grafana overview adds `Degraded Dependencies` and `Served Chain Age` panels. The dependency gauge also reports a writer's `reorg_window_exceeded` halt read through ingest control, which the reader already reports as its own cause, so exclude that cause when alerting on degraded dependencies. While the writer's live mempool hydrates or rebuilds from its node, native query and wallet-mode compatibility report `ingest_control` with `node_unavailable` and the `stream_disconnected` failure class, even when its own node probe passes, so `ZinderDependencyDegraded` fires when that lasts longer than two minutes. Wallet-mode `zinder-compat-lightwalletd` now admits ingest control at startup as native query does: it refuses to start against an endpoint whose service, network, contract revision, or required methods differ, and it reports an ingest-control outage under `degraded` as `ingest_control` while `GetMempoolStream`, `GetMempoolTx`, and unmined `GetTransaction` fail. The single-host wallet-serving container no longer restarts while ingest reports `upstream_not_ready`. It also stays up while ingest reports `syncing` and query's `/readyz` relays the writer's `upstream_not_ready` under `ingest_control`, as happens while Zebra resyncs, or the writer mempool's `node_unavailable` while ingest's `syncing` cause reports `"lag_blocks": null` with a `current_height` at or above `target_height`, as happens when only the node's mempool feed fails. A writer that reports a numeric `lag_blocks` or trails its target height stays on the usual one-hour unready tolerance. It restarts on `node_unavailable`, whether ingest reports it or query relays it, only after 24 hours. The reference Compose topology starts query and compatibility once the ingest container has started rather than once it is healthy. ([#257](https://github.com/ZcashFoundation/zinder/pull/257))
- `zinder-query`, `zinder-compat-lightwalletd`, and `zinder-projector` now start while the node is down. They no longer probe the node or read its activation table at startup, and only `zinder-ingest` still reports the `connect_node` startup phase. Every reader opens storage on the network-upgrade schedule the canonical writer admitted, and when it opens a store that ingest has not opened yet it waits for ingest's first admission until `storage.initial_catchup_timeout_ms` passes (for the projector, `projector.fence_convergence_timeout_seconds`), however many convergence attempts that takes. `[node]` is now optional for query and wallet-mode compatibility: without it they serve storage only and advertise no broadcast. Any node setting, from TOML, `ZINDER_NODE__*`, or the command line, still requires `node.json_rpc_addr`, so a misspelled address variable fails startup instead of silently disabling broadcast. With it they advertise `wallet.broadcast.transaction_v1` at once and check the node the first time they reach it, requiring `sendrawtransaction` in `rpc.discover`, an activation table that matches the store's schedule, and a best chain that holds the store's tip block (read with `getblockhash`). Until that check passes, broadcasts fail with `UNAVAILABLE` and `NODE_UNAVAILABLE` and no transaction is sent, `/readyz` lists `node_source` under `degraded`, and `ServerInfo.node` is empty. Query and wallet-mode compatibility also start when the node's cookie file is missing, empty, or unreadable, and verify the node once the file holds credentials, while `zinder-ingest` still exits at startup without a readable cookie file for the node it starts on. `zinder-projector` and compact-blocks compatibility now refuse to start with `[node]`, `--node-json-rpc-addr`, or any `ZINDER_NODE__*` variable, so remove those settings from their configuration files, environment, and service units; the bundled projector configuration, Compose file, and single-host entrypoint already do. Explorer now reads the network-upgrade table from its wallet query and refreshes it every minute, instead of serving an empty table when its node was down at startup. For Rust users of `zinder-query`, `WalletServingQuery::from_serving_pair_slot` and `from_admitted_native_serving_pair` no longer take a broadcaster or activation table, `with_node_broadcast` replaces `from_probed_node_source` and `from_admitted_native_sources`, `WalletServingPairConfig` drops `network_upgrade_activations`, and `spawn_wallet_node_readiness_probe` takes an optional `NodeBroadcast` and the serving-pair slot. ([#258](https://github.com/ZcashFoundation/zinder/pull/258))
- Every Zinder service binary (`zinder-ingest`, `zinder-projector`, `zinder-query`, `zinder-compat-lightwalletd`, `zinder-explorer`, and `zinder-compat-cipherscan`) now refuses to start when `RUST_LOG` is set to a value that is not a valid log filter, such as `zinder=verbose`, instead of silently logging at `info`. The binary exits non-zero before it reads configuration or opens storage and prints the variable, its value, and the parse error to stderr. A `RUST_LOG` that is not valid Unicode fails the same way. An unset, empty, or whitespace-only `RUST_LOG` still selects `info`. A bare word such as `zinder` remains valid and enables every level for that target. Check `RUST_LOG` in your deployments before upgrading. For library users, `zinder_runtime::install_tracing_subscriber` now returns `Result<(), TracingSubscriberError>` and reports a second install as an error instead of panicking. ([#270](https://github.com/ZcashFoundation/zinder/pull/270))

### Fixed

- `zinder-compat-lightwalletd` now parses each `GetTaddressBalanceStream` address as it arrives and rejects the stream with `INVALID_ARGUMENT` as soon as an address is invalid or the 257th distinct address arrives, instead of buffering every streamed address until the client finishes sending. `GetTaddressBalance` and `GetTaddressBalanceStream` count a repeated address once, so a request that repeats one address more than 256 times is now served. Every transparent-address lookup in `zinder-query`, `zinder-compat-lightwalletd`, and `zinder-explorer`, including `GetTaddressTxids`, `GetTaddressTransactions`, `GetAddressUtxos`, and `GetAddressUtxosStream`, now refuses address text longer than 64 bytes before parsing it, so an oversized address no longer ties up a request in Base58 decoding. ([#265](https://github.com/ZcashFoundation/zinder/pull/265))
- `zinder-compat-lightwalletd` now sends `SubtreeRoot.completingBlockHash` from `GetSubtreeRoots` in RPC byte order, as reference lightwalletd does. It previously sent the hash in internal byte order, so clients that compare it with lightwalletd or with a block explorer saw reversed bytes. Subtree roots and completing heights are unchanged. ([#266](https://github.com/ZcashFoundation/zinder/pull/266))
- `zinder-compat-lightwalletd` `GetMempoolStream` now sends each transaction once per stream, as reference lightwalletd does. It previously could send a transaction twice when it appeared in the mempool snapshot and as a live event, or was evicted and added again. When the tip-change signal closes, for example while the runtime shuts down, the stream now ends with `UNAVAILABLE` instead of `OK`, so a wallet does not treat it as a new block. One stream sends at most 100,000 distinct transactions between tip changes and then ends with `UNAVAILABLE`, which wallets retry. ([#267](https://github.com/ZcashFoundation/zinder/pull/267))
- `zinder-compat-lightwalletd` now refuses `Ping` with `FAILED_PRECONDITION` in both serving modes, as reference lightwalletd does unless it is started with `--ping-very-insecure`. Wallet serving previously answered with zero counts, and compact-blocks serving answered `UNIMPLEMENTED`. ([#268](https://github.com/ZcashFoundation/zinder/pull/268))
- `zinder-ingest` now answers read-only canonical-control requests, including `WriterStatus`, while its writer waits on a node request, backs off after a node failure, or decides on an endpoint switch. Before, a stalled node delayed these requests by up to `node.request_timeout_secs` per call, so wallet readers could miss their 15-second writer-status deadline and stop serving once the stall outlasted `storage.serving_pair_staleness_ceiling_ms`, although stored reads were still possible. Mempool appends, pruning, leases, and owner checkpoints sent during the wait are still applied in arrival order once it ends. ([#261](https://github.com/ZcashFoundation/zinder/pull/261))
- `zinder-ingest` with only `[node]` configured now checks at startup that the node's block 0 is the configured network's genesis block, and refuses to start when it is not. Before, only deployments with `[node_fallbacks.N]` ran this check, so a checkpointed build pointed at a node on another chain, such as a Regtest node behind a `zcash-testnet` configuration, could store that chain under the configured network. A refused startup logs `node_endpoints_unavailable` and reports `node_unavailable` with failure class `configuration` on `/readyz`. A node that cannot serve block 0 yet, for example while it is still starting, fails startup as unreachable, as before. ([#275](https://github.com/ZcashFoundation/zinder/pull/275))

### Security

- Public listeners now bound the denial-of-service paths lightwalletd fixed in GHSA-5xg7-x58j-m5vr, GHSA-4wjx-vhhv-vc8c, GHSA-xrx5-jc6q-9h8r, GHSA-p4pq-3cf7-45rv, GHSA-8vh8-6jg3-8f5v, and GHSA-w24w-x7vw-f2w8. On `zinder-compat-lightwalletd`, `zinder-query`, and `zinder-explorer`, a gRPC request larger than 2 MiB now fails with `OUT_OF_RANGE` (it was 4 MiB), and each process receives at most 32 requests at once per pool, shared fairly across connections; a request over the limit fails with `UNAVAILABLE`, and one that has not arrived within 20 seconds fails with `DEADLINE_EXCEEDED`. Client-streaming calls, such as `GetTaddressBalanceStream` and gRPC reflection, draw on a separate pool and fail with `DEADLINE_EXCEEDED` after 20 seconds without a message. A response whose client stops reading for 60 seconds ends with `DEADLINE_EXCEEDED`. Requests whose list fields hold far more elements than any handler accepts fail with `INVALID_ARGUMENT` before they are decoded. Broadcasts share a 16 MiB transaction budget per process; a broadcast over it fails with `UNAVAILABLE` and the new `BROADCAST_BUDGET_EXHAUSTED` reason, which `zinder-client` retries. The ops endpoint and the Cipherscan REST adapter now enforce header, body, and write-stall deadlines and a connection cap. Keep the ops endpoint on loopback or a private network, and limit concurrent connections per client at your proxy, because many connections can still fill a pool. New metrics: `zinder_grpc_request_receive_refusals_total`, `zinder_grpc_request_receive_timeouts_total`, `zinder_grpc_request_receive_evictions_total`, `zinder_grpc_response_send_stalls_total`, and `zinder_query_broadcast_budget_refusals_total`. ([#283](https://github.com/ZcashFoundation/zinder/pull/283))
